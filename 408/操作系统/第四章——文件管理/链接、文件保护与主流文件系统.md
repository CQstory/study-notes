# 链接、文件保护与主流文件系统

### 硬链接与软链接（重要考点）

| | 硬链接（Hard Link） | 软链接（Symbolic Link） |
|:---|:---|:---|
| **本质** | 新增一个目录项指向**同一个 inode** | 创建一个**新文件**，内容是目标文件的**路径名** |
| **类比** | 同一个人有两张身份证 | 一张写着"去找张三"的便签纸 |
| **链接计数** | 目标文件计数 **+1** | 目标文件计数**不变** |
| **inode 号** | 与原文件**相同** | 与原文件**不同**（自己有独立 inode） |
| **跨文件系统** | ❌ 不可以 | ✅ 可以 |
| **对目录** | ❌ 不允许（防环路） | ✅ 允许 |
| **删除原文件后** | 仍可访问（数据还在） | **失效**（悬空/死链） |
| **典型用途** | 备份、共享、防误删 | 快捷方式、跨分区引用 |

#### 举例

```
原文件：/home/user/report.txt → inode=42

【硬链接】ln report.txt backup.txt
  目录项：report.txt → inode=42
          backup.txt → inode=42  ← 同一个 inode！
  inode 42 链接计数 = 2

【软链接】ln -s report.txt shortcut.txt
  目录项：report.txt   → inode=42
          shortcut.txt → inode=99 ← 全新的 inode！
  inode 99 的内容 = "/home/user/report.txt"（纯文本路径）
```

#### 删除原文件后的行为

```
硬链接：rm report.txt → 链接计数 2→1 → 数据仍在 → backup.txt 正常
软链接：rm report.txt → 链接计数 1→0 → 数据释放 → shortcut.txt 悬空
```

> [!tip] 现实场景类比
> - **硬链接**：适合"同一文件需要多个名字但不能分散管理"的场景（如全局 skill 文件，多个目录项指向同一份本体）
> - **软链接**：适合"本体在一处、引用者多处且跨目录结构"的场景（如 `.agent/skills/` 存本体，在 `.claude/`、`.codex/` 等目录下放软链接指向本体）

#### 判断题速记

| 题目 | 答案 |
|:---|:---:|
| "硬链接和原文件有相同的 inode 号" | ✅ |
| "软链接和原文件有相同的 inode 号" | ❌ |
| "删除原文件后硬链接失效" | ❌（仍可访问） |
| "删除原文件后软链接失效" | ✅（悬空） |
| "创建硬链接会增加目标文件链接计数" | ✅ |
| "创建软链接会增加目标文件链接计数" | ❌ |
| "硬链接可以跨文件系统" | ❌ |
| "软链接可以跨文件系统" | ✅ |

### 文件保护与存取控制（权限模型）

> 文件保护是操作系统防止未授权访问的机制。核心是**存取控制**：每个文件/目录有一组权限位，按用户身份决定能做什么。

#### 权限位：r(4) + w(2) + x(1)

| 权限 | 对**文件**的含义 | 对**目录**的含义 |
|:---:|:---|:---|
| `r`(4) | 读取文件内容 | **列出目录内容**（`ls`） |
| `w`(2) | 修改文件内容 | **在目录中创建/删除文件** |
| `x`(1) | 执行该文件 | **进入该目录**（`cd`） |

> [!important] 关键区分
> **"增删列"是目录级操作 → 看目录权限；"读改执行"是文件级操作 → 看文件权限。**
> 不存在单独的"添加权限""删除权限"——它们被目录的 `w` 位统一管辖。

#### 三类用户 × 三组权限

```
权限表示：[Owner][Group][Other]，每组 = r(4)+w(2)+x(1)

例：755 = 7(111) + 5(101) + 5(101)
         属主全权   组只读+执行  其他人只读+执行
```

**常见权限值**：

| 权限 | Owner | Group | Other | 场景 |
|:---:|:---:|:---:|:---:|:---|
| **777** | `rwx` | `rwx` | `rwx` | 全开（危险） |
| **775** | `rwx` | `rwx` | `r-x` | 协作目录 |
| **755** | `rwx` | `r-x` | `r-x` | 目录/脚本（最常见） |
| **700** | `rwx` | `---` | `---` | 私有目录 |
| **644** | `rw-` | `r--` | `r--` | 普通文件（默认） |
| **600** | `rw-` | `---` | `---` | 密钥/密码文件 |

#### 权限检查流程

```
用户请求访问某文件：
1. 读入 inode → 得到属主、属组、权限位
2. 判断请求者身份：
   ├─ 是属主？ → 用 Owner 权限
   ├─ 是属组成员？ → 用 Group 权限
   └─ 都不是 → 用 Other 权限
3. 检查对应权限位是否允许该操作
```

#### 操作与权限对应表

| 操作 | 需要什么权限 | 检查对象 |
|:---|:---|:---|
| 列出目录内容（`ls`） | `r` | **目录** |
| 在目录中创建文件 | `w` | **父目录** |
| 删除文件 | `w` | **父目录** |
| 读取文件内容 | `r` | **文件** |
| 修改文件内容 | `w` | **文件** |
| 执行文件 | `x` | **文件** |
| 进入目录（`cd`） | `x` | **目录** |

> [!warning] 反直觉考点
> 删除文件检查的是**父目录的 `w` 权限**，不是文件本身的权限。即使文件权限是 777，若父目录无 `w` 权限，仍然删不了。

#### 文件保护机制详解

##### （1）存取控制矩阵（理论模型）

一个二维表，行 = 用户，列 = 文件，格 = 该用户对该文件的权限：

```
        文件A   文件B   文件C   目录D
alice   rw      r       rwx     rw
bob     r       r       r       r-x
carol   rw      rw      -       -
```

- **优点**：概念清晰，可完整描述整个系统的权限关系
- **缺点**：极度稀疏（大多数格为空），存储浪费巨大
- **实际不用**，但它是理解 ACL 和权能表的理论基础

**两种分解方式**：
- 按**列**切（每个文件一行）→ 得到 **ACL**
- 按**行**切（每个用户一行）→ 得到 **权能表**

##### （2）访问控制表（ACL，Access Control List）

**本质**：存取控制矩阵**按列**切割——每个文件附带一张"谁能访问我"的表。

**与权限位（rwx）的区别**：

| | 权限位（rwx） | ACL |
|:---|:---|:---|
| **粒度** | 只分三类：属主/同组/其他 | 为**每个用户/组**单独指定 |
| **灵活度** | 粗（3×3 = 9 位） | 细（任意用户 × 任意权限） |
| **存储** | inode 中 9 位 | 每文件附带一张表 |
| **典型系统** | Linux 默认 | Windows NTFS、POSIX ACL |

**ACL 结构示例**：

```
文件 "report.txt" 的 ACL：
┌──────────────┬──────────┐
│ 主体          │ 权限     │
├──────────────┼──────────┤
│ 用户 alice    │ rw       │
│ 用户 bob     │ r        │
│ 组 dev-team  │ rwx      │
│ 其他所有人    │ -        │
└──────────────┴──────────┘
```

**权限检查流程**（与权限位不同）：

```
用户 bob 请求读取 report.txt：
1. 读入 report.txt 的 ACL
2. 逐行匹配：
   ├─ 找到"用户 bob" → 权限 = r → 有读 → ✅ 允许
   └─ 未找到 → 继续匹配"组"、"其他"
3. 全部不匹配 → 拒绝
```

**优缺点**：

| 优点 | 缺点 |
|:---|:---|
| 精确到每个用户 | 表可能很长（上千用户） |
| 增删用户权限方便 | 存储开销大 |
| 查"某文件的权限"很快 | 查"某用户能访问哪些文件"很慢（需遍历所有文件） |

##### （3）权能表（Capability）

**本质**：存取控制矩阵**按行**切割——每个用户/进程持有"我能访问什么"的表。

```
进程 alice 的权能表：
┌──────────────┬──────────┐
│ 客体          │ 权限     │
├──────────────┼──────────┤
│ 文件A        │ rw       │
│ 文件B        │ r        │
│ 目录D        │ rw       │
└──────────────┴──────────┘
```

**与 ACL 的对比**：

| | ACL | 权能表 |
|:---|:---|:---|
| 视角 | "这个文件允许谁来访问" | "这个进程能访问什么" |
| 查"某文件的权限" | ✅ 快（直接读文件的 ACL） | ❌ 慢（需遍历所有权能表） |
| 查"某用户能访问什么" | ❌ 慢（需遍历所有文件的 ACL） | ✅ 快（直接读该用户的权能表） |
| 撤销权限 | ✅ 容易（改文件的 ACL） | ❌ 困难（需找到所有持有该权能的进程） |
| 典型系统 | Windows NTFS、Linux | 分布式系统、微内核 |

##### （4）口令保护（Password）

**机制**：为文件/目录设置口令，访问时需输入正确口令。

```
文件 "secret.txt"：口令 = "abc123"

用户请求读取 → 系统提示输入口令 → 比对 → 匹配则允许
```

**口令的存储方式**：

| 方式 | 安全性 | 说明 |
|:---|:---:|:---|
| **明文存储** | ❌ 极不安全 | 一旦泄露立即可用 |
| **哈希存储**（MD5/SHA） | ✅ | 不可逆，验证时对比哈希值 |
| **加盐哈希**（salt + hash） | ✅✅ | 每个用户不同盐值，防彩虹表攻击 |

**优缺点**：

| 优点 | 缺点 |
|:---|:---|
| 实现简单 | 记住大量口令困难 |
| 单文件级别保护 | 口令可被偷窥/暴力破解 |
| 不依赖用户身份认证系统 | 无法细粒度控制（只有能/不能） |

##### （5）加密保护（Encryption）

**机制**：文件内容在磁盘上以**密文**存储，无密钥不可读。

```
明文 "Hello, World!"
    │  加密（密钥 K）
    ▼
密文 "x9#kL2@pQz..."（磁盘上）
    │  解密（密钥 K）
    ▼
明文 "Hello, World!"（给用户）
```

**两种加密方式**：

| | 对称加密 | 非对称加密 |
|:---|:---|:---|
| **密钥** | 加密解密**同一把**钥匙 | 公钥加密 + 私钥解密 |
| **速度** | 快 | 慢 |
| **典型算法** | AES、DES、3DES | RSA、ECC |
| **文件保护场景** | 加密文件内容（大量数据） | 加密密钥本身（数字信封） |

**文件系统中的加密层次**：

| 层次 | 说明 | 示例 |
|:---|:---|:---|
| **文件级加密** | 只加密单个文件 | Linux eCryptfs |
| **目录级加密** | 加密整个目录 | Windows EFS（加密文件系统） |
| **磁盘级加密** | 加密整个分区/磁盘 | BitLocker（Windows）、LUKS（Linux） |

**加密 vs 口令的区别**：
- 口令保护：文件本身**明文**存在磁盘，只是"门"锁住了
- 加密保护：文件本身是**密文**，即使"门"被撬开也读不懂

## 4.1.8 主流文件系统全景（了解即可）

> 本节梳理真实操作系统使用的文件系统类型，帮助理解 §4.1.5~§4.1.7 抽象机制的具体落地。408 不深考具体文件系统版本差异，但需知道典型代表。

### Linux / UNIX 系

| 文件系统 | 所属 | 核心特点 |
|:---|:---|:---|
| **UFS** | 早期 UNIX | 最早的 inode 文件系统 |
| **ext2** | Linux | inode + 超级块 + 块组；无日志 |
| **ext3** | Linux | ext2 + **日志**（journal），崩溃恢复快 |
| **ext4** | Linux（主流） | 支持 1EB 卷、延迟分配、extent |
| **XFS** | Linux（Red Hat） | 64 位日志，超大文件性能好 |
| **Btrfs** | Linux | 写时复制（CoW）、快照、内建 RAID |
| **ZFS** | Solaris/FreeBSD | 集卷管理+文件系统一体，校验和 |

### Windows 系

| 文件系统 | 所属 | 核心特点 |
|:---|:---|:---|
| **FAT12/16** | DOS/Win95 | FAT 链式管理；最大 2GB |
| **FAT32** | Win98 | 最大 32GB 卷、4GB 文件 |
| **exFAT** | Win7+ | 突破 4GB 限制；U 盘常用 |
| **NTFS** | WinNT 至今（主流） | 日志+权限+加密+压缩；最大 16EB |
| **ReFS** | Win Server 2012+ | 面向大数据，自动校验修复 |

### macOS / iOS 系

| 文件系统 | 所属 | 核心特点 |
|:---|:---|:---|
| **HFS+** | macOS（~2017） | 日志式，B树目录 |
| **APFS** | macOS 2017+ | 写时复制、快照、加密、空间共享 |

### 特殊/虚拟文件系统

| 文件系统 | 用途 |
|:---|:---|
| **tmpfs** | 内存文件系统（/tmp），断电丢失 |
| **procfs / sysfs** | 伪文件系统，将内核信息暴露为文件（/proc, /sys） |
| **devfs** | 设备文件（/dev），设备即文件 |

> [!tip] 408 掌握程度
> 只需知道：**ext 系列用 inode**（§4.1.6）、**FAT 系列用显式链接**（§4.1.5）、**NTFS 用索引分配**。不需要记具体版本参数。

## 考点总结

### 高频考点

1. **文件物理结构对比**：连续分配、链接分配（隐式/显式）、索引分配的优缺点
2. **inode设计思想**：为什么将文件名与文件描述信息分离
3. **混合索引计算**：直接地址+多次间接的文件最大大小计算
4. **FAT与隐式链接的区别**：显式链接如何支持随机访问
5. **目录结构对比**：四种目录结构的特点和适用场景

### 易错点

1. 顺序文件不一定按关键字有序，也可以按时间顺序（串结构）
2. 索引文件的索引表本身是定长记录的顺序文件
3. 隐式链接只支持顺序访问，显式链接（FAT）支持随机访问
4. inode方式下，目录项只包含文件名和inode号，不包含文件的物理地址等信息
5. 无环图目录中，文件的删除需要检查链接计数

### 计算题型

1. **混合索引计算**：给定块大小、地址大小、各级索引项数，计算文件最大长度
2. **FAT表计算**：给定FAT表内容，求文件占用的磁盘块号序列
3. **位示图地址计算**：给定字号、位号，求对应的磁盘块号（见[[第四章——文件管理/存储空间管理与考点|存储空间管理与考点]]）
