# 操作系统体系结构

[[第一章——计算机系统概述|← 返回目录]]

## 一、操作系统体系结构概述

操作系统的体系结构是指操作系统内部各模块的组织方式和层次关系。不同的体系结构影响着操作系统的性能、可靠性、可维护性和可扩展性。

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 正确性 | 系统行为必须与设计规范一致 |
| 高效性 | 系统应充分利用硬件资源 |
| 可维护性 | 系统应易于修改和扩展 |
| 可移植性 | 系统应能在不同硬件平台上运行 |
| 可靠性 | 系统应能正确处理异常情况 |
| 安全性 | 系统应防止非法访问和破坏 |

## 二、大内核与微内核

### 2.1 大内核（宏内核 / 单体内核）

**大内核**将进程管理、内存管理、文件系统、设备驱动等所有操作系统核心功能都放在内核中运行。

**大内核的结构特点：**

```
┌─────────────────────────────────────┐
│            用户应用程序              │
├─────────────────────────────────────┤
│         系统调用接口                 │
├─────────────────────────────────────┤
│  进程管理 │ 内存管理 │ 文件系统      │
│  设备驱动 │ 网络协议 │ IPC          │
│  ........ │ ........ │ ........     │
├─────────────────────────────────────┤
│            硬件                     │
└─────────────────────────────────────┘
         ↑ 全部运行在内核态 ↑
```

**大内核的优点：**

| 优点 | 说明 |
|------|------|
| 性能高 | 各模块之间可以直接调用，无需频繁切换到用户态 |
| 效率高 | 内核内部通信开销小，函数调用直接高效 |

**大内核的缺点：**

| 缺点 | 说明 |
|------|------|
| 可靠性差 | 一个模块出错可能导致整个内核崩溃 |
| 可维护性差 | 代码量大，模块间耦合度高，修改困难 |
| 可扩展性差 | 添加新功能可能影响已有功能 |
| 开发难度大 | 内核代码复杂，调试困难 |

**典型代表：** UNIX、Linux、MS-DOS

### 2.2 微内核

**微内核**只将最基本的功能（如进程调度、进程通信、中断处理）放在内核中，其他功能（如文件系统、设备驱动等）作为用户态的服务进程运行。

**微内核的结构特点：**

```
┌─────────────────────────────────────┐
│            用户应用程序              │
├─────────────────────────────────────┤
│  文件服务 │ 设备服务 │ 网络服务      │
│  （用户态服务进程）                  │
├─────────────────────────────────────┤
│         微内核（内核态）             │
│  ┌───────────┬──────────┬─────────┐ │
│  │ 进程调度   │  IPC    │ 中断处理│ │
│  └───────────┴──────────┴─────────┘ │
├─────────────────────────────────────┤
│            硬件                     │
└─────────────────────────────────────┘
```

**微内核的优点：**

| 优点 | 说明 |
|------|------|
| 可靠性高 | 服务进程在用户态运行，出错不会导致内核崩溃 |
| 可维护性好 | 各服务进程相互独立，修改一个不影响其他 |
| 可扩展性好 | 添加新服务只需添加新的用户态进程 |
| 可移植性好 | 微内核代码量小，易于移植到不同平台 |
| 安全性好 | 服务进程隔离，攻击面小 |

**微内核的缺点：**

| 缺点 | 说明 |
|------|------|
| 性能较低 | 频繁的用户态/内核态切换，开销大 |
| 效率较低 | 服务进程间通信需要通过IPC，效率低于直接函数调用 |

**典型代表：** Minix、QNX、Mach、HarmonyOS（部分采用微内核设计）

### 2.3 大内核与微内核的对比

| 比较项 | 大内核 | 微内核 |
|--------|--------|--------|
| 内核大小 | 大 | 小 |
| 内核态功能 | 所有OS核心功能 | 仅进程调度、IPC、中断处理 |
| 性能 | 高（直接函数调用） | 较低（需要IPC和模式切换） |
| 可靠性 | 较低（一个bug可能崩溃） | 高（服务隔离） |
| 可维护性 | 差（耦合度高） | 好（模块独立） |
| 可扩展性 | 差 | 好 |
| 可移植性 | 差 | 好 |
| 用户态/内核态切换 | 少 | 多 |
| 代表系统 | Linux、UNIX | Minix、QNX、Mach |

> [!important] 考点
> - 微内核的核心思想是：**内核越小越好**，只保留最基本的功能
> - 微内核的性能瓶颈在于频繁的**状态切换**和**进程间通信（IPC）**
> - 408考试中常以选择题形式考查大内核与微内核的优缺点对比

## 三、分层结构

### 3.1 分层结构的概念

**分层结构**将操作系统分为若干层次，从底层（靠近硬件）到高层（靠近用户），每一层只能调用其下层提供的服务，不能调用上层。

**分层结构示意图：**

```
第0层：硬件
    ↑
第1层：CPU调度、基本中断处理
    ↑
第2层：内存管理
    ↑
第3层：设备管理
    ↑
第4层：文件系统
    ↑
第5层：用户接口（命令/程序接口）
    ↑
用户程序
```

### 3.2 分层结构的优缺点

| 优点 | 说明 |
|------|------|
| 易于调试和验证 | 可以逐层调试，底层正确后再开发上层 |
| 易于维护 | 层次分明，修改一层不影响其他层 |
| 结构清晰 | 各层功能明确，依赖关系单向 |

| 缺点 | 说明 |
|------|------|
| 效率较低 | 层次间调用有开销，底层功能可能被上层频繁调用 |
| 难以定义层次 | 合理划分各层功能边界比较困难 |
| 灵活性差 | 层次固定，调用关系不能跨层，某些功能可能需要绕路 |

> [!tip] 考点
> - 分层结构最大的问题是**难以合理定义各层边界**
> - 第0层是硬件，最底层；最高层是用户接口
> - 每层只能调用**紧邻的下层**，不能跨层调用

---

## 四、模块化结构

### 4.1 模块化结构的概念

**模块化结构**将操作系统按功能划分为多个独立的模块（如进程管理模块、内存管理模块、文件管理模块等），各模块之间通过明确的接口进行通信。

**模块化结构示意图：**

```
┌─────────────────────────────────────┐
│            主控模块                 │
├──────┬──────┬──────┬──────┬────────┤
│进程  │内存  │文件  │设备  │其他    │
│管理  │管理  │管理  │管理  │模块    │
├──────┴──────┴──────┴──────┴────────┤
│            硬件                     │
└─────────────────────────────────────┘
```

### 4.2 模块化结构的优缺点

| 优点 | 说明 |
|------|------|
| 提高了OS的正确性和可靠性 | 模块间接口清晰，便于独立开发和测试 |
| 增强了可维护性 | 修改一个模块不影响其他模块 |
| 加速了OS开发过程 | 多个模块可以并行开发 |
| 灵活性好 | 可以方便地添加或替换模块 |

| 缺点 | 说明 |
|------|------|
| 模块间接口定义困难 | 接口设计需要仔细规划 |
| 模块间可能存在循环依赖 | 需要严格控制模块间的调用关系 |
| 调试困难 | 模块间的交互可能产生难以追踪的问题 |

> [!tip] 考点
> - 模块化结构的核心是**模块划分**和**接口定义**
> - 模块化结构是现代操作系统常用的设计方式
> - Linux内核采用的就是模块化设计（可加载内核模块 LKM）

## 五、内核态与用户态切换过程

### 5.1 为什么需要两种运行模式

计算机系统中的资源需要保护，防止用户程序直接访问和修改关键系统资源。因此引入了两种处理器运行模式：

| 模式 | 用途 | 权限 |
|------|------|------|
| 内核态（管态/核心态） | 运行OS内核程序 | 可执行所有指令，访问所有资源 |
| 用户态（目态） | 运行用户应用程序 | 只能执行非特权指令 |

**实现机制：**
- 在CPU中设置一个**模式位**（如PSW中的bit）
- 0 表示内核态，1 表示用户态（或反之，取决于具体架构）
- 特权指令只能在内核态下执行，否则产生异常

### 5.2 用户态到内核态的切换

用户态切换到内核态的**唯一途径**是**中断或异常**。

**触发方式：**

| 触发方式 | 说明 | 示例 |
|----------|------|------|
| 系统调用（陷阱/陷入） | 用户程序主动请求OS服务 | `read()`, `write()`, `fork()` |
| 外中断 | 外部设备发出中断信号 | I/O完成中断、时钟中断 |
| 异常 | CPU执行指令时产生的内部错误 | 缺页、除零、非法指令 |

**切换过程：**

```
用户态执行
    │
    ├─ ① 发生中断/异常/系统调用
    │
    ├─ ② CPU检测到中断信号
    │
    ├─ ③ 硬件自动完成：
    │      - 保存当前PC（程序计数器）到栈或特定寄存器
    │      - 保存当前PSW（程序状态字）
    │      - 根据中断类型查中断向量表
    │      - 将模式位从"用户态"改为"内核态"
    │      - 加载中断服务程序的PC
    │
    ├─ ④ 开始执行中断服务程序（内核态）
    │
    ├─ ⑤ 执行完毕后：
    │      - 恢复保存的PC和PSW
    │      - 将模式位从"内核态"改为"用户态"
    │
    └─ ⑥ 返回用户态继续执行
```

### 5.3 内核态到用户态的切换

内核态切换到用户态通过执行一条**特权指令**完成，通常是一条中断返回指令（如x86的`iret`）。

**切换过程：**

```
内核态执行中断服务程序
    │
    ├─ ① 执行中断返回指令（如 iret）
    │
    ├─ ② 硬件自动完成：
    │      - 从栈中恢复之前的PC
    │      - 从栈中恢复之前的PSW（包含用户态模式位）
    │      - 模式位被恢复为"用户态"
    │
    └─ ③ 返回用户态继续执行被中断的程序
```

> [!important] 考点
> - **用户态 → 内核态**：通过中断/异常（唯一途径）
> - **内核态 → 用户态**：通过执行特权指令（如iret）
> - 模式切换是由**硬件**自动完成的，不是由软件完成的
> - 每次系统调用至少需要**两次**模式切换（用户→内核→用户）

### 5.4 模式切换的开销

| 开销项目 | 说明 |
|----------|------|
| 保存上下文 | 需要保存PC、PSW、通用寄存器等 |
| 修改模式位 | 硬件修改PSW中的模式位 |
| 查中断向量表 | 根据中断号查找对应处理程序入口 |
| 切换栈 | 从用户栈切换到内核栈（或反之） |
| 恢复上下文 | 恢复之前保存的寄存器值 |

> [!tip] 考点
> - 系统调用的开销远大于普通函数调用（因为涉及模式切换）
> - 这是微内核性能较低的根本原因（频繁的模式切换）

## 六、系统调用的分类与过程

### 6.1 系统调用的概念回顾

**系统调用**是操作系统为应用程序提供的服务接口，是用户程序请求操作系统内核服务的**唯一方式**。

**系统调用的本质：**
- 应用程序通过**陷入指令（trap）**主动发起
- CPU从用户态切换到内核态
- 内核执行对应的服务程序
- 返回结果并切换回用户态

### 6.2 系统调用的详细分类

#### 按功能分类

| 分类 | 功能说明 | 典型系统调用（Linux） |
|------|----------|----------------------|
| **进程控制** | 创建/终止进程、获取/设置进程属性 | `fork()`, `execve()`, `wait()`, `exit()`, `getpid()` |
| **进程通信** | 进程间数据传递与同步 | `pipe()`, `shmget()`, `shmat()`, `msgget()`, `semget()` |
| **文件操作** | 文件的创建/删除/读/写/属性操作 | `open()`, `close()`, `read()`, `write()`, `lseek()`, `unlink()` |
| **文件系统操作** | 目录的创建/删除/遍历 | `mkdir()`, `rmdir()`, `opendir()`, `readdir()`, `stat()` |
| **设备管理** | 设备的请求/释放/读写 | `ioctl()`, `mmap()`, `read()`, `write()` |
| **内存管理** | 内存的分配/释放/映射 | `brk()`, `sbrk()`, `mmap()`, `munmap()`, `mprotect()` |
| **信息维护** | 获取/设置系统或进程信息 | `gettimeofday()`, `uname()`, `getrlimit()`, `sysinfo()` |

#### 按调用方式分类

| 调用方式 | 说明 | 示例 |
|----------|------|------|
| 直接系统调用 | 程序中直接使用系统调用 | `syscall()` |
| 通过库函数间接调用 | 通过C库函数封装后调用 | `printf()` → `write()` |

> [!tip] 考点
> - `printf()` 是库函数，它内部会调用 `write()` 系统调用
> - `strlen()` 是纯库函数，不涉及系统调用
> - 并非所有库函数都会引发系统调用

### 6.3 系统调用的执行过程（详细）

#### 步骤详解

```
┌─────────────────────────────────────────────┐
│ 用户程序                                     │
│                                              │
│  ① 设置系统调用参数                           │
│     - 将参数存入通用寄存器（Linux使用寄存器传参）│
│     - 或将参数压入用户栈                       │
│     - 设置系统调用号（如 eax 寄存器）          │
│                                              │
│  ② 执行陷入指令（trap / int 0x80 / syscall） │
│     ↓                                        │
├────── 用户态/内核态边界 ──────────────────────┤
│ 内核态                                       │
│                                              │
│  ③ 硬件自动保存用户态上下文                    │
│     - PC、PSW、通用寄存器 → 内核栈            │
│     - 切换到内核栈                            │
│     - 修改PSW模式位为内核态                   │
│                                              │
│  ④ 根据系统调用号查系统调用表                  │
│     - sys_call_table[调用号] → 服务程序入口    │
│                                              │
│  ⑤ 执行系统调用服务程序                        │
│     - 如 sys_read()、sys_write() 等           │
│     - 执行实际的内核操作                       │
│                                              │
│  ⑥ 将返回值存入寄存器（如 eax）               │
│                                              │
│  ⑦ 执行中断返回指令（iret / sysret）           │
│     - 恢复用户态上下文                         │
│     - 切换回用户栈                             │
│     - 修改PSW模式位为用户态                    │
│     ↓                                        │
├────── 内核态/用户态边界 ──────────────────────┤
│ 用户程序                                     │
│                                              │
│  ⑧ 获取返回值，继续执行                       │
└─────────────────────────────────────────────┘
```

#### 系统调用过程代码示例

```c
// ===== 用户态代码 =====
#include <unistd.h>
#include <fcntl.h>

int main() {
    // write() 是一个系统调用
    // 它最终会通过陷入指令进入内核态
    write(1, "Hello, OS!\n", 12);

    // open() 是一个系统调用
    int fd = open("test.txt", O_RDONLY);

    // read() 是一个系统调用
    char buf[64];
    int n = read(fd, buf, sizeof(buf));

    // close() 是一个系统调用
    close(fd);

    return 0;
}

// ===== 内核态中的大致处理流程 =====
// 当用户程序调用 write(1, "Hello, OS!\n", 12) 时：

// 1. C库函数 write() 将参数放入寄存器：
//    - ebx = 1 (文件描述符)
//    - ecx = "Hello, OS!\n" (缓冲区地址)
//    - edx = 12 (字节数)
//    - eax = 4 (write 的系统调用号)

// 2. 执行陷入指令：int 0x80 (x86) 或 syscall (x86_64)

// 3. CPU切换到内核态，跳转到系统调用入口

// 4. 内核根据 eax 中的调用号(4)，查系统调用表：
//    sys_call_table[4] → sys_write

// 5. 执行 sys_write()，将数据写入标准输出

// 6. 返回值写入 eax，执行 iret 返回用户态
```

### 6.4 系统调用号与系统调用表

系统调用通过**系统调用号**来标识不同的服务。操作系统维护一张**系统调用表**，将系统调用号映射到对应的内核函数。

**Linux 系统调用表示例（部分）：**

| 系统调用号 | 系统调用名称 | 功能 |
|-----------|-------------|------|
| 0 | `sys_read` | 从文件描述符读取数据 |
| 1 | `sys_write` | 向文件描述符写入数据 |
| 2 | `sys_open` | 打开文件 |
| 3 | `sys_close` | 关闭文件 |
| 39 | `sys_mkdir` | 创建目录 |
| 57 | `sys_fork` | 创建进程 |
| 59 | `sys_execve` | 执行程序 |

> [!important] 考点
> - 系统调用号是系统调用表的索引
> - 不同操作系统的系统调用号和系统调用表不同
> - 系统调用表存放在内核空间，用户程序无法直接访问

### 6.5 系统调用的参数传递方式

| 传递方式 | 说明 | 优缺点 |
|----------|------|--------|
| 通过寄存器传递 | 将参数存入通用寄存器 | 速度快，但参数个数受限于寄存器数量 |
| 通过栈传递 | 将参数压入用户栈或内核栈 | 参数个数不受限，但速度较慢 |
| 通过内存块传递 | 将参数放在内存中，将地址通过寄存器传递 | 适合大量参数的情况 |

**Linux的参数传递：**
- x86：通过栈传递（int 0x80 方式）
- x86_64：通过寄存器传递（syscall 方式）
  - 第1个参数 → `rdi`
  - 第2个参数 → `rsi`
  - 第3个参数 → `rdx`
  - 系统调用号 → `rax`

## 七、操作系统体系结构对比总结

### 7.1 三种结构对比

| 比较项 | 大内核 | 微内核 | 分层结构 | 模块化结构 |
|--------|--------|--------|----------|------------|
| 内核规模 | 大 | 小 | 中等 | 可变 |
| 性能 | 高 | 较低 | 中等 | 较高 |
| 可靠性 | 较低 | 高 | 中等 | 较高 |
| 可维护性 | 差 | 好 | 较好 | 好 |
| 可扩展性 | 差 | 好 | 差 | 好 |
| 模块耦合度 | 高 | 低 | 中等 | 低 |
| 典型系统 | Linux | Minix | MULTICS | Linux(模块化) |

### 7.2 现代操作系统的发展趋势

```
大内核 ──→ 模块化大内核（如 Linux）
    │
    └──→ 微内核（如 Minix、QNX）
            │
            └──→ 混合内核（如 Windows NT、macOS XNU）
                  结合了大内核的性能和微内核的可靠性
```

> [!tip] 考点
> - **Linux** 采用的是**模块化的大内核**（宏内核 + 可加载模块）
> - **Windows NT** 采用的是**混合内核**（Hybrid Kernel）
> - **macOS/iOS** 的 XNU 内核也是混合内核（Mach微内核 + BSD组件）
> - **HarmonyOS** 采用微内核设计

### 8.2 易错点

1. **Linux不是纯微内核**：Linux是大内核（宏内核），但支持可加载内核模块（LKM），具有模块化特征
2. **陷入指令不是特权指令**：陷入指令在用户态执行，用于触发到内核态的切换
3. **系统调用号不是中断号**：系统调用号用于查系统调用表，中断号用于查中断向量表
4. **微内核性能低的原因**：不是因为代码效率低，而是因为频繁的用户态/内核态切换和IPC通信
5. **分层结构不能跨层调用**：第N层只能调用第N-1层，不能直接调用第N-2层

### 8.3 记忆口诀

- **大内核 vs 微内核**：大快不稳，小稳不快
- **系统调用过程**：设参数 → 陷入 → 查表 → 执行 → 返回
- **模式切换**：用户到内核靠中断，内核到用户靠特权指令
