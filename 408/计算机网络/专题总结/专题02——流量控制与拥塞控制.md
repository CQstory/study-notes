# 专题02——流量控制与拥塞控制

> [!abstract] 知识定位
> 流量控制与拥塞控制是计网**最容易被混为一谈**的一对概念，也是**计算题最密集**的区域。本专题以「辨析 → 四层全景 → 计算模板 → 状态机 → 现代演进 → 易错点」六段展开，重点补足正文笔记缺失的部分：**网络层拥塞控制手段、漏桶与令牌桶、QoS（IntServ/DiffServ）、主动队列管理（RED/CoDel）、拥塞崩溃、CUBIC 与 BBR**。
>
> 正文已有内容的交叉引用：链路层滑动窗口三协议见 [[第三章——数据链路层]] §3.3，TCP 流控与拥塞控制见 [[第五章——传输层]] §5.5–5.7。

## 一、主题问题引入

> [!question] 两个必须先回答的问题
> **① 流量控制和拥塞控制到底有什么区别？** 两者都在"限制发送速率"，为什么 TCP 要同时做两件事？
>
> **② 既然有了流量控制，为什么还需要拥塞控制？** 接收方说自己能收 100 个报文段，发送方就可以发 100 个吗？

**答案是：不行。** 因为接收方的缓冲区够大，不代表**沿途的路由器**扛得住。

| 场景 | 谁跟不上 | 谁来通知 | 用什么变量限制 |
|:-----|:---------|:---------|:---------------|
| 接收方处理能力弱、缓冲区小 | **接收方** | 接收方**明确告知** | **rwnd**（接收窗口） |
| 沿途链路带宽不足、路由器缓存满 | **网络** | **没人通知，只能猜** | **cwnd**（拥塞窗口） |

$$发送窗口 = \min(rwnd,\ cwnd)$$

**取两者中的较小值** —— 这一条公式就是两个机制的全部耦合关系。

> [!tip] 一句话类比
> - **流量控制**：你给朋友寄快递，朋友说"我家只能堆 5 箱，别多寄" → **对方明确告诉你上限**
> - **拥塞控制**：高速公路堵车了，没人给你打电话，你只能看导航红不红、上次走了多久 → **靠观察推断，自己决定慢下来**

## 二、核心概念辨析

### 2.1 十一维对比总表

| 对比维度 | **流量控制** Flow Control | **拥塞控制** Congestion Control |
|:---------|:--------------------------|:--------------------------------|
| **目的** | 防止发送方压垮**接收方** | 防止注入网络的分组过多压垮**网络** |
| **保护对象** | 接收方的缓冲区与处理能力 | 链路带宽与路由器缓存 |
| **控制范围** | **点对点**（一对一，端到端） | **全局**（整个子网所有节点） |
| **反馈来源** | 接收方**显式通告** rwnd | **隐式推断**（丢包、RTT 变化） |
| **反馈信道** | ACK 报文中的**窗口字段** | **无专用信道**，发送方自行观察 |
| **核心变量** | **rwnd**（接收窗口） | **cwnd**（拥塞窗口） |
| **变量存放位置** | rwnd 在**报文中传输**，双方都知道 | **cwnd 只存在于发送方本地，不在报文中！** |
| **主要机制** | 滑动窗口、零窗口探测 | 慢启动、拥塞避免、快重传、快恢复 |
| **所在层次** | 数据链路层、传输层 | 网络层、传输层 |
| **失效后果** | 接收方丢帧 / 丢报文段 | 吞吐下降、时延激增，极端时**拥塞崩溃** |
| **能否精确感知** | **能**（接收方直接告知） | **不能**（这正是难点的根源） |

> [!warning] 最容易被忽略的一行
> **cwnd 是发送方的本地变量，从不在 TCP 报文中传输，接收方完全不知道 cwnd 是多少。**
>
> 而 rwnd 是接收方通过 TCP 首部的**窗口字段**明确告知的。两者一个"公开"一个"私有"，这是选择题的高频陷阱。

### 2.2 两者的耦合

```
                 ┌──────────────────────────┐
   接收方通告 →  │  rwnd（接收窗口，公开）    │
                 └────────────┬─────────────┘
                              │
                        取较小值 min
                              │
                 ┌────────────┴─────────────┐
   发送方自算 →  │  cwnd（拥塞窗口，私有）    │
                 └──────────────────────────┘
                              ↓
                     实际发送窗口 swnd
                              ↓
                 未确认字节数 ≤ swnd 才能继续发
```

**三种典型情形**：

| 情形 | 判断 | 说明 |
|:-----|:-----|:-----|
| rwnd < cwnd | **接收方是瓶颈** | 网络通畅但对端处理不过来（如慢速磁盘写入的服务器） |
| cwnd < rwnd | **网络是瓶颈** | 对端能收但路上堵（长肥管道、高丢包率链路） |
| rwnd = 0 | **接收方缓冲区满** | 发送方停发，启动**坚持定时器** |

### 2.3 单位陷阱（跨层易混）

| 层次 | 窗口的单位 | 变量名 |
|:-----|:-----------|:-------|
| **数据链路层**（停等 / GBN / SR） | **帧**（frame）个数 | $W_T$、$W_R$ |
| **传输层**（TCP） | **字节**（byte） | rwnd、cwnd |

> [!warning] 这是跨层最大的坑
> 链路层的滑动窗口"窗口 = 3"指**3 个帧**；TCP 的"窗口 = 3000"指**3000 个字节**。
>
> TCP 首部窗口字段是 **16 bit**，所以 rwnd 最大 65535 **字节**（约 64 KB），不是 65535 个报文段。
>
> 正因如此才有了**窗口缩放选项**（Window Scale，RFC 1323）：最大移位 14 位，窗口可达 $65535 × 2^{14}$ ≈ **1 GB**。

## 三、四个层次的流控与拥塞控制全景

### 3.1 数据链路层：滑动窗口三协议

详见 [[第三章——数据链路层]] §3.3。此处只给**窗口上限与确认方式**的对比，这是计算题的入口。

| 对比项 | **停止-等待 SW** | **后退 N 帧 GBN** | **选择重传 SR** |
|:-------|:-----------------|:------------------|:----------------|
| **发送窗口 $W_T$** | 1 | $1 < W_T ≤ 2^n - 1$ | $W_T ≤ 2^{n-1}$ |
| **接收窗口 $W_R$** | 1 | **1** | $W_R = W_T ≤ 2^{n-1}$ |
| **确认方式** | 逐个确认 | **累积确认** | **逐个独立确认** |
| **重传范围** | 出错的那一帧 | **出错帧及其后所有已发帧全部重传** | **只重传出错的那一帧** |
| **接收方缓存** | 1 帧 | 1 帧（必须按序交付） | $W_R$ 帧（可乱序暂存） |
| **信道利用率** | 低 | 中 | **高** |
| **实现复杂度** | 最简 | 中 | 最复杂 |

其中 $n$ 为**帧序号所占的比特位数**。

> [!important] 为什么 GBN 的上限是 $2^n - 1$ 而不是 $2^n$？
> 假设 $n = 3$（序号 0~7），若允许 $W_T = 8$：
> 发送方发出 0~7 全部 8 帧，接收方全部正确接收并发送 ACK，但**ACK 全部丢失**。
> 发送方超时后重发 0~7；此时接收方的窗口已滑动到期望接收"新一轮的 0~7"，**它无法区分这是新帧还是旧帧的重传** → 数据错误。
>
> 只要 $W_T ≤ 2^n - 1 = 7$，接收窗口内就不会出现序号回绕的歧义。

> [!important] 为什么 SR 的上限是 $2^{n-1}$？
> SR 的接收方会**乱序缓存**，因此约束更严：$W_T + W_R ≤ 2^n$。
> 通常取 $W_T = W_R$，于是 $2W ≤ 2^n$ → $W ≤ 2^{n-1}$。
>
> $n = 3$ 时：GBN 可开到 $W_T = 7$，SR 只能开到 $W_T = W_R = 4$。**看起来 SR 更"弱"，但因为 SR 不重传正确帧，实际效率更高。**

### 3.2 传输层：TCP 流量控制

详见 [[第五章——传输层]] §5.5。核心补充：

#### 糊涂窗口综合征（Silly Window Syndrome, SWS）

接收方每次只腾出一点点空间就通告小窗口，导致发送方发出大量**小报文段** —— 40 字节首部承载几字节数据，效率暴跌。

| 病因方 | 症状 | 解决方案 |
|:-------|:-----|:---------|
| **接收方** | 应用读取慢，缓冲区一点点腾出就急着通告 | **Clark 方案**：等到能容纳**一个完整 MSS** 或缓冲区**腾出一半**时才通告窗口 |
| **发送方** | 应用每次只 write 几个字节就触发发送 | **Nagle 算法**：积累到 **1 个 MSS** 或**收到前一个 ACK** 后才发送 |

#### 零窗口死锁与坚持定时器

```
接收方缓冲区满 → 通告 rwnd = 0 → 发送方停发
      ↓
接收方应用读走数据，缓冲区腾空 → 发送 rwnd 更新报文
      ↓
   ★ 若这个更新报文丢失 ★
      ↓
接收方以为发送方知道了，干等；发送方以为对方还是 0，也干等
      ↓
   【死锁】—— 双方永久等待
```

**解决：坚持定时器（Persistence Timer）+ 零窗口探测**

发送方收到 rwnd = 0 后启动坚持定时器，到期发送一个 **1 字节的零窗口探测报文**，迫使接收方回一个 ACK（其中携带**最新的 rwnd**）。打破死锁。

### 3.3 传输层：TCP 拥塞控制四大算法

详见 [[第五章——传输层]] §5.6。此处补充**精确的增量规则**与**两种丢包的差异化反应**。

| 算法 | 触发条件 | cwnd 变化规则 | 增长形态 |
|:-----|:---------|:--------------|:---------|
| **慢启动** | 连接建立后 / 超时后 | **每收到 1 个 ACK：cwnd += 1 MSS** → **每个 RTT 翻倍** | **指数** |
| **拥塞避免** | cwnd ≥ ssthresh | **每个 RTT：cwnd += 1 MSS**（实现上每 ACK 加 $MSS × MSS/cwnd$） | **线性** |
| **快重传** | 收到 **3 个冗余 ACK** | **不改窗口**，立即重传丢失报文段（不等超时） | — |
| **快恢复** | 快重传之后 | ssthresh = cwnd/2；**cwnd = ssthresh**；转入**拥塞避免** | 线性 |

> [!warning] "慢启动"其实增长极快
> 慢启动是**指数增长**（每 RTT 翻倍：1→2→4→8→16→32...），比拥塞避免的线性增长快得多。
>
> 名字叫"慢"是因为**起点低**（从 1 MSS 开始），不是增长慢。这是最经典的概念误解。

> [!important] 超时 vs 3 个冗余 ACK：反应完全不同（★必考）
>
> | 触发信号 | ssthresh | cwnd | 进入阶段 | 剧烈程度 |
> |:---------|:---------|:-----|:---------|:---------|
> | **超时（RTO 到期）** | cwnd / 2 | **1 MSS** | **慢启动** | **剧烈** |
> | **3 个冗余 ACK** | cwnd / 2 | **ssthresh（= cwnd/2）** | **拥塞避免** | **温和** |
>
> **为什么要区别对待？**
> - **超时**意味着网络**严重拥塞** —— 连重复 ACK 都传不回来，说明大面积丢包 → 必须剧烈降速，几乎从零开始
> - **3 个冗余 ACK** 意味着**只是个别分组丢失** —— 后续分组仍能到达接收方并触发 ACK，说明网络还在正常工作 → 温和降速即可

> [!note] 教材差异提示
> **RFC 5681** 规定快恢复后 $cwnd = ssthresh + 3\ MSS$（因为 3 个冗余 ACK 表示已有 3 个分组成功离开网络，腾出了空间）。
> **谢希仁教材与 408 通常简化为 $cwnd = ssthresh$**。做题以题干/教材为准，但要知道有这个差异。

### 3.4 网络层：拥塞控制（★正文笔记缺失）

#### 拥塞的定义

对网络中某一资源的需求**超过了该资源所能提供的可用部分**：

$$\sum 到达分组数 > \sum 服务能力 \quad\Rightarrow\quad 拥塞$$

#### 开环控制 vs 闭环控制

| | **开环控制** Open Loop | **闭环控制** Closed Loop |
|:--|:----------------------|:-------------------------|
| **思想** | **事前预防** —— 设计时就确保不会拥塞 | **事后反应** —— 检测到拥塞再调整 |
| **手段** | 准入控制、流量整形、决定何时丢弃分组、资源预留 | 监测 → 传递信息 → 调整系统状态 |
| **优点** | 不需要反馈，无反馈时延 | 能适应动态变化 |
| **缺点** | 无法应对突发流量 | 反馈有延迟，可能引起**振荡** |

#### 闭环控制的三个步骤

| 步骤 | 内容 | 具体做法 |
|:-----|:-----|:---------|
| **① 监测** | 检测何时、何地发生拥塞 | 丢包率、平均队列长度、超时重传次数、平均分组时延、**时延抖动** |
| **② 传递信息** | 把拥塞信息传到能采取行动的地方 | **显式**：路由器发拥塞通知分组；**隐式**：靠丢包/时延让端系统自己推断（Internet 的选择） |
| **③ 调整** | 改变系统运行状态 | 调节发送速率、丢弃分组、改变路由、拒绝新连接 |

#### 网络层的具体控制手段

| 手段 | 说明 |
|:-----|:-----|
| **负载丢弃（Load Shedding）** | 路由器缓存满时**有策略地**丢弃分组。**葡萄酒策略**：新到的分组先丢（像新酒先喝）还是旧分组先丢，取决于应用类型（文件传输丢旧的、实时流丢新的） |
| **流量感知路由** | 选择路径时把链路负载纳入度量，主动避开拥塞链路 |
| **准入控制（Admission Control）** | 虚电路网络中，检测到拥塞时**拒绝建立新连接** |
| **流量调节（Traffic Regulation）** | 漏桶、令牌桶（见 §3.5） |
| **资源预留** | IntServ / RSVP（见 §3.6） |
| **公平队列（Fair Queuing）** | 每个流独立排队，避免单个流独占缓存 |

> [!important] Internet 的选择：隐式 + 端系统负责
> Internet 的网络层（IP）**不做任何拥塞控制** —— 路由器只会尽力转发，缓存满了就丢。
>
> 拥塞控制的责任**完全压在端系统的 TCP 上**，且只能靠**隐式信号**（丢包、RTT）推断。
>
> 这与 [[第一章——计算机网络体系结构]] §1.1.2 的「数据报服务 vs 虚电路服务」「端到端原则」是同一条设计主线：**核心简单，智能放边缘**。

### 3.5 流量整形：漏桶 vs 令牌桶（★正文笔记缺失）

| 对比项 | **漏桶** Leaky Bucket | **令牌桶** Token Bucket |
|:-------|:----------------------|:------------------------|
| **物理模型** | 桶底有小孔的水桶：**无论进水多快，出水速率恒定** | 以固定速率 $r$ 往桶里放令牌，桶容量 $b$；**有令牌才能发分组** |
| **输出速率** | **恒定**（绝对平滑） | **可变**，允许突发到链路速率 $M$ |
| **是否允许突发** | **不允许**（严格恒速） | **允许**（桶满时可一次性用掉全部令牌） |
| **长期平均速率** | = 出水速率 $ρ$ | = 令牌生成速率 $r$ |
| **最大突发量** | **0** | **$b·M/(M-r)$**（不只是 $b$！） |
| **超出时行为** | 桶满则**溢出丢弃** | 无令牌则**等待或丢弃** |
| **典型应用** | 严格限速、流量整形（shaping）、管制（policing） | 允许突发的限速、ATM/帧中继的 UPC、现代 QoS |

#### 漏桶计算

设突发输入速率 $λ$，持续时长 $T$，漏桶出水速率 $ρ$，桶容量 $C$：

- 进水总量 = $λT$
- 出水总量 = $ρ(T + S)$，其中 $S$ 是突发结束后继续排空的时间
- 平衡时 $ρ(T+S) = λT$ → $S = T(λ-ρ)/ρ$
- **不溢出的条件**：$C ≥ (λ-ρ)T$

#### 令牌桶计算（★高频）

设令牌生成速率 $r$、桶容量 $b$、链路最大速率 $M$（$M > r$）：

在时间 $S$ 内可发送的最大数据量同时受两个约束：

$$b + rS = MS \quad\Rightarrow\quad S = \frac{b}{M-r}$$

- **最大突发持续时间** $S = b/(M-r)$
- **最大突发传输量** $= MS = \dfrac{b·M}{M-r}$

> [!example] 令牌桶例题
> 令牌桶容量 $b = 250$ KB，令牌生成速率 $r = 5$ MB/s，链路最大速率 $M = 25$ MB/s。求最大突发时间与突发量。
>
> **统一单位**：$b = 250$ KB，$r = 5000$ KB/s，$M = 25000$ KB/s
>
> $S = 250 / (25000 - 5000) = 250 / 20000 = 0.0125$ s = **12.5 ms**
>
> 最大突发量 $= M × S = 25000 × 0.0125 = $ **312.5 KB**
>
> **验算**：$b + rS = 250 + 5000 × 0.0125 = 250 + 62.5 = 312.5$ KB ✓

> [!warning] 最大突发量不是 b
> 很多人误答"最大突发量 = 桶容量 $b$ = 250 KB"。**错。**
>
> 在突发的 12.5 ms 期间，**令牌还在持续生成**（$r × S = 62.5$ KB），所以实际能发 $b + rS = 312.5$ KB。
>
> 只有当 $M \to \infty$ 时突发量才趋近于 $b$。

### 3.6 QoS 与主动队列管理（★正文笔记缺失）

#### IntServ vs DiffServ

| 对比项 | **IntServ**（集成服务） | **DiffServ**（区分服务） |
|:-------|:------------------------|:-------------------------|
| **粒度** | **每流**（per-flow） | **每类**（per-class） |
| **信令** | 需要 **RSVP** 逐跳预留资源 | **不需要信令** |
| **路由器状态** | 每个流一份状态 → **状态爆炸，不可扩展** | 无每流状态 → **可扩展** |
| **复杂处理位置** | 所有路由器 | **仅边界路由器**，核心路由器只看 DSCP 简单转发 |
| **服务类型** | 保证服务、受控负载服务 | **EF**（加速转发）、**AF**（确保转发）、**BE**（尽力而为） |
| **保证强度** | 强（可给时延上界） | 弱（统计性优先） |
| **现状** | 基本未部署 | **现代 Internet QoS 主流** |

#### 主动队列管理（AQM）

| 算法 | 思想 | 特点 / 解决的问题 |
|:-----|:-----|:------------------|
| **Tail Drop**（尾部丢弃） | 队列满就丢新到的分组 | 导致**全局同步**（见下） |
| **RED**（随机早期检测） | 队列长度超阈值时**随机**提前丢弃，给 TCP 早期信号 | **打破全局同步**；缺点是参数难调 |
| **CoDel**（受控时延） | 监测分组在队列中的**停留时间**，超过 target（默认 5 ms）持续 interval（默认 100 ms）就丢弃 | **无参数**，直接对抗 Bufferbloat |
| **FQ-CoDel** | CoDel + 公平队列 | Linux / OpenWrt 默认 |
| **PIE** | 基于时延的概率标记 | DOCSIS 3.1 电缆调制解调器 |

> [!important] 全局同步（Global Synchronization）
> **Tail Drop 的核心问题**：队列一满，**所有流的分组一起被丢** → 所有 TCP **同时降窗** → 链路利用率骤降 → 队列迅速排空 → 所有 TCP **同时恢复** → 再次拥塞。
>
> 结果：链路利用率呈**剧烈锯齿振荡**，平均利用率远低于容量。
>
> **RED 的解法**：**随机**丢弃，让不同流在**不同时刻**收到信号、在**不同时刻**降窗，从而错开节奏、平滑利用率曲线。
>
> **注意：RED 的目的不是"减少丢包"，而是"打散丢包的时间分布"。**

## 四、计算题模板

### 4.1 滑动窗口协议的信道利用率

**停等协议**：

$$η = \frac{T_D}{T_D + RTT + T_A}$$

**GBN / SR（窗口为 $W$）**：

$$η = \min\left(1,\ \frac{W × T_D}{T_D + RTT + T_A}\right)$$

**跑满信道所需的最小窗口**：

$$W ≥ 1 + \frac{RTT + T_A}{T_D} \approx 1 + \frac{RTT}{T_D}$$

其中 $T_D$ = 数据帧发送时延，$T_A$ = ACK 帧发送时延（常忽略），$RTT ≈ 2 ×$ 传播时延。

> [!example] 例题：为什么停等协议不可行
> 链路 1 Gb/s，RTT = 20 ms，帧长 1000 B。
>
> $T_D = 1000 × 8 / 10^9 = 8$ μs
>
> 停等效率 $η = 8 / (8 + 20000) = 8 / 20008 ≈$ **0.04%**
>
> 需窗口 $W ≥ 1 + 20000/8 = 2501$ 帧才能跑满。

### 4.2 TCP 拥塞窗口逐 RTT 演算（★必练）

> [!example] 完整演算例题
> 设 MSS = 1 KB，连接建立后 cwnd = 1 MSS，初始 ssthresh = 16 MSS。
> 在 **cwnd = 24** 时发生**超时**；重新慢启动后在 **cwnd = 16** 时收到 **3 个冗余 ACK**。
> 求各轮次的 cwnd。
>
> | RTT 轮次 | cwnd (MSS) | ssthresh | 阶段 | 事件 |
> |:--------:|:----------:|:--------:|:-----|:-----|
> | 1 | 1 | 16 | 慢启动 | 初始 |
> | 2 | 2 | 16 | 慢启动 | 指数翻倍 |
> | 3 | 4 | 16 | 慢启动 | |
> | 4 | 8 | 16 | 慢启动 | |
> | 5 | **16** | 16 | 慢启动→**拥塞避免** | cwnd 达到 ssthresh，**转线性** |
> | 6 | 17 | 16 | 拥塞避免 | 每 RTT +1 |
> | 7 | 18 | 16 | 拥塞避免 | |
> | 8 | 19 | 16 | 拥塞避免 | |
> | 9 | 20 | 16 | 拥塞避免 | |
> | 10 | 21 | 16 | 拥塞避免 | |
> | 11 | 22 | 16 | 拥塞避免 | |
> | 12 | 23 | 16 | 拥塞避免 | |
> | 13 | **24** | **12** | **超时！** | ssthresh = 24/2 = 12，**cwnd 重置为 1** |
> | 14 | 1 | 12 | 慢启动 | 重新开始 |
> | 15 | 2 | 12 | 慢启动 | |
> | 16 | 4 | 12 | 慢启动 | |
> | 17 | 8 | 12 | 慢启动 | |
> | 18 | **12** | 12 | 慢启动→**拥塞避免** | 达到 ssthresh |
> | 19 | 13 | 12 | 拥塞避免 | |
> | 20 | 14 | 12 | 拥塞避免 | |
> | 21 | 15 | 12 | 拥塞避免 | |
> | 22 | **16** | **8** | **3 个冗余 ACK** | ssthresh = 16/2 = 8，**cwnd = ssthresh = 8** |
> | 23 | **8** | 8 | **拥塞避免**（不是慢启动！） | 快恢复 |
> | 24 | 9 | 8 | 拥塞避免 | |
> | 25 | 10 | 8 | 拥塞避免 | |
>
> **三个关键判读点**：
> - 第 5 轮：cwnd **等于** ssthresh 时**转入拥塞避免**（不再翻倍）
> - 第 13 轮：超时 → cwnd **回到 1**，进入**慢启动**
> - 第 22~23 轮：快重传 → cwnd **减半到 ssthresh**，直接进入**拥塞避免**，**不回 1、不慢启动**

### 4.3 发送窗口综合题

> [!example] 例题：rwnd 与 cwnd 取小
> 某时刻接收方通告 rwnd = 32 KB，发送方本地 cwnd = 24 KB，MSS = 1 KB。
> 问发送方最多还能发多少未确认数据？
>
> 发送窗口 $= \min(32,\ 24) = $ **24 KB**
>
> 即最多 24 个报文段的未确认数据在途。**瓶颈是网络（cwnd < rwnd）**。

### 4.4 Mathis 公式：TCP Reno 的吞吐上限

$$吞吐 ≤ \frac{MSS}{RTT × \sqrt{p}}$$

其中 $p$ 为丢包率。

> [!example] 例题：长肥管道的绝望
> MSS = 1460 B，RTT = 100 ms，丢包率 $p = 10^{-4}$。
>
> 吞吐 $= \dfrac{1460 × 8}{0.1 × \sqrt{10^{-4}}} = \dfrac{11680}{0.1 × 0.01} = \dfrac{11680}{0.001} = 11.68 × 10^6$ bit/s ≈ **11.7 Mb/s**
>
> **即使链路是 1 Gb/s，TCP Reno 也只能跑到约 11.7 Mb/s！**
>
> 关键：**这个上限与链路带宽无关**，只由 RTT 和丢包率决定。RTT 越长、丢包越多，吞吐越低 —— 这就是**长肥管道（LFN）** 问题，也是 BBR 诞生的直接动因（见 §6.3）。

## 五、TCP 拥塞控制状态机

```
                     ┌─────────────────────┐
        连接建立 →   │      慢启动          │  cwnd 每 RTT 翻倍（指数）
                     │  cwnd = 1 MSS 起     │
                     └──────────┬──────────┘
                                │ cwnd ≥ ssthresh
                                ↓
                     ┌─────────────────────┐
                     │     拥塞避免         │  cwnd 每 RTT +1（线性）
                     └──────┬───────┬──────┘
                            │       │
              ┌─────────────┘       └─────────────┐
        超时（RTO 到期）                    3 个冗余 ACK
              │                                   │
              ↓                                   ↓
   ┌────────────────────┐              ┌────────────────────┐
   │ ssthresh = cwnd/2  │              │ ssthresh = cwnd/2  │
   │ cwnd = 1 MSS       │              │ cwnd = ssthresh    │
   │ → 回到【慢启动】    │              │ → 进入【拥塞避免】  │
   └────────────────────┘              └────────────────────┘
        （剧烈降速）                        （温和降速，快恢复）
```

**四个算法的职责划分**：

| 算法 | 属于哪一组 | 职责 |
|:-----|:-----------|:-----|
| **慢启动** | 窗口**增长** | 从低起点快速探测可用带宽 |
| **拥塞避免** | 窗口**增长** | 接近容量时谨慎线性逼近 |
| **快重传** | 丢包**响应** | 尽早重传，缩短丢包造成的停顿 |
| **快恢复** | 丢包**响应** | 温和降窗，避免吞吐塌方 |

> [!tip] 记忆：AIMD
> 整体策略是 **AIMD（Additive Increase Multiplicative Decrease，加性增、乘性减）**：
> - **加性增**：拥塞避免阶段每 RTT **+1 MSS**（线性）
> - **乘性减**：出问题时 ssthresh 和 cwnd **× 1/2**
>
> AIMD 被证明能在多个竞争流之间**收敛到公平分配**，这是它成为 Internet 基石的理论原因。
>
> 慢启动是 AIMD 之外的**额外加速阶段**（指数增长），只在起点和超时后使用。

## 六、现代演进（深挖）

### 6.1 传统算法的三重困境

| 困境 | 表现 | 根因 |
|:-----|:-----|:-----|
| **长肥管道跑不满** | 1 Gb/s × 150 ms 的链路，Reno 只能跑到十几 Mb/s | Mathis 公式：吞吐与 RTT、丢包率绑定，与带宽无关 |
| **无线链路误判** | Wi-Fi/4G 的随机误码丢包被当成拥塞，窗口腰斩 | **丢包 ≠ 拥塞**，但 Reno 只有丢包这一个信号 |
| **缓冲区膨胀** | 下载时游戏 ping 从 20 ms 飙到 800 ms | 路由器缓冲区过大 → 排队时延暴涨 → RTT 失真 |

### 6.2 CUBIC（Linux 默认）

把窗口增长改为**三次函数**而非线性：

$$W(t) = C(t - K)^3 + W_{max}$$

其中 $K = \sqrt[3]{W_{max}β/C}$，$β = 0.7$（降窗系数），$t$ 是距上次拥塞的时间。

| 特性 | 说明 |
|:-----|:-----|
| **窗口增长形态** | 靠近 $W_{max}$ 时增长慢（谨慎探测），远离时增长快（迅速占领带宽） |
| **不依赖 RTT** | 用**真实时间** $t$ 而非 RTT 计数驱动，对长 RTT 链路更友好 |
| **对 LFN 的表现** | 明显优于 Reno |
| **仍依赖丢包** | **没有解决无线误判问题** |

### 6.3 BBR（Google，2016）

**范式转变：不再以丢包为拥塞信号，改为主动测量网络容量。**

$$BDP = BtlBw × RTprop$$

- **BtlBw**（Bottleneck Bandwidth）：瓶颈链路的最大带宽，取近期**最大值**
- **RTprop**（Round-Trip propagation time）：最小往返时延（即**无排队时**的纯传播时延），取近期**最小值**
- 两者的乘积就是**管道容量**，发送速率维持在 BDP 附近：**既不欠载（跑不满）也不过载（造成排队）**

| 状态 | 作用 |
|:-----|:-----|
| **Startup** | 类似慢启动，指数增长直到测得 BtlBw 不再上升 |
| **Drain** | 排空 Startup 阶段积累的队列 |
| **ProbeBW** | 主状态。周期性以 1.25× / 0.75× 速率探测，持续更新 BtlBw |
| **ProbeRTT** | 每 10 s 一次，把 cwnd 压到 4 个分组以排空队列，重新测量真实 RTprop |

| 对比 | Reno | CUBIC | **BBR** |
|:-----|:-----|:------|:--------|
| **拥塞信号** | 丢包 | 丢包 | **不用丢包** |
| **窗口驱动** | RTT 计数 | 真实时间 | **测得的 BDP** |
| **长肥管道** | 差 | 较好 | **优秀** |
| **高误码无线** | **灾难** | 差 | **好** |
| **缓冲区占用** | 大（填满才丢包） | 大 | **小**（主动保持队列近空） |
| **公平性** | — | 与 Reno 竞争时占优 | 与 CUBIC 共存时**可能不公平**（曾受批评） |

### 6.4 QUIC 把拥塞控制搬到用户态

| 变化 | 意义 |
|:-----|:-----|
| **用户态实现** | 可**快速迭代**，不需要改内核、不需要等 OS 升级。Google 能在几个月内部署新算法 |
| **算法可插拔** | 默认 CUBIC 变种，可切换 BBR、BBRv2、Copa |
| **精确丢包判定** | packet number **单调递增、永不复用** → 消除 TCP 的**重传歧义**（不再需要 Karn 算法） |
| **无队头阻塞** | 多路复用的流之间互不阻塞，单个流丢包不拖累其他流 |
| **内建加密** | TLS 1.3 融合进握手，1-RTT 建连、重连 0-RTT |

### 6.5 缓冲区膨胀（Bufferbloat）与 AQM 的关系

```
路由器缓冲区做得很大（几 MB ~ 几十 MB）
        ↓
TCP 的丢包信号迟迟不触发（要填满整个缓冲区才丢）
        ↓
排队时延暴涨到几百 ms 甚至秒级
        ↓
RTT 严重失真 → BBR 测不准 RTprop、Reno 反应更迟钝
        ↓
交互应用（游戏、视频会议、SSH）体验崩溃
        ↓
【缓冲区膨胀 Bufferbloat】
```

**解决路线**：
- **减小缓冲区**（粗暴但有效）
- **AQM**：RED（随机早期丢弃）→ **CoDel / FQ-CoDel**（直接控制排队时延）→ PIE
- **换算法**：BBR 主动保持队列近空，天然抗 Bufferbloat

> [!info]- 深挖：为什么缓冲区会被越做越大？
> 2000 年代初有一篇影响深远的论文提出「**缓冲区应按 BDP  sizing**」，即 $缓冲区 = RTT × 带宽$。这在**单一长流**场景下是对的，但被厂商过度推广：
>
> - 核心路由器缓冲区做到几十 MB
> - 家用路由器为了"跑满带宽测试"也堆大缓冲
> - 结果：**单流吞吐好看了，多流交互体验崩了**
>
> 这是典型的**用一个指标（吞吐）优化、牺牲另一个指标（时延）** 的工程失误。Jim Gettys 在 2011 年前后系统性地提出 Bufferbloat 概念，直接推动了 CoDel 与 FQ-CoDel 的诞生，也间接促成 Linux 默认队列规则改为 fq_codel。

## 七、拥塞崩溃与三种"卡死"的辨析

### 7.1 拥塞崩溃（Congestion Collapse）

> [!important] 1986 年 10 月的真实事件
> Internet 骨干吞吐量从 **32 Kbps 骤降到 40 bps** —— 下降了**三个数量级**。
>
> **原因：重传风暴。** 网络拥塞 → 分组丢失 → 端系统超时重传 → 重传分组加剧拥塞 → 更多丢失 → 更多重传。**正反馈死亡螺旋**。
>
> 网络里塞满了分组，但绝大多数是**无用的重复重传**，有效吞吐趋近于零。
>
> **解决**：Van Jacobson 于 1988 年提出拥塞控制算法（慢启动 / 拥塞避免 / 快重传 / 快恢复的原型），**拯救了 Internet**。这就是 TCP 拥塞控制的历史起源。

**拥塞崩溃的判定特征**：网络**负载极高**但**有效吞吐极低**，且**重传占比极高**。

### 7.2 拥塞 vs 死锁 vs 饥饿

| 对比项 | **拥塞** | **死锁** | **饥饿** |
|:-------|:---------|:---------|:---------|
| **本质** | 资源需求 > 供给 | 循环等待，互相持有对方所需资源 | 某进程长期得不到资源 |
| **系统状态** | 性能下降，但**仍在推进** | **完全停滞** | 系统正常，**个别**进程停滞 |
| **受害范围** | **全局**（所有流） | 参与循环的那几个 | 个别进程 |
| **能否自愈** | **能**（拥塞控制主动降速） | **不能**（需外力干预） | 可能（竞争者结束后有机会） |
| **典型层次** | 网络层 / 传输层 | 资源分配 | 调度 / 资源分配 |

> [!warning] 但极端拥塞可能演变成死锁
> **存储转发死锁（Store-and-Forward Deadlock）**：多个路由器的缓冲区**互相占满**，A 等 B 腾出空间、B 等 C、C 等 A → 形成循环等待，拥塞升级为**真死锁**，无法自愈。
>
> 防范手段：缓冲区配额限制、**虚通道（virtual channel）**、Dally-Seitz 理论。
>
> 这正好对应操作系统 [[专题01——饥饿问题|OS 专题01——饥饿问题]] 中"饥饿不一定是死锁，但死锁必然伴随饥饿"的辨析结构。

## 八、易错点汇总

### 8.1 概念辨析类

| # | 易错点 | 正解 |
|:-:|:-------|:-----|
| 1 | 流量控制和拥塞控制是一回事吗？ | **不是**。流控保护**接收方**（点对点、显式通告 rwnd）；拥塞控制保护**网络**（全局、隐式推断 cwnd） |
| 2 | 发送窗口等于哪个？ | $\min(rwnd,\ cwnd)$，**取小者** |
| 3 | cwnd 会出现在 TCP 报文里吗？ | **不会**。cwnd 是发送方**本地变量**，接收方不知道它的值。rwnd 才通过窗口字段传输 |
| 4 | rwnd 是谁定的？ | **接收方**根据自己缓冲区剩余空间通告；cwnd 是**发送方**根据网络状况自己算 |
| 5 | UDP 有流量控制或拥塞控制吗？ | **都没有**。所以实时应用用 UDP 时可能压垮网络 —— 这正是 QUIC 要在 UDP 之上自己实现拥塞控制的原因 |

### 8.2 算法行为类

| # | 易错点 | 正解 |
|:-:|:-------|:-----|
| 6 | "慢启动"增长慢吗？ | **不慢，是指数增长**（每 RTT 翻倍）。"慢"指**起点低**（从 1 MSS 开始） |
| 7 | 慢启动阶段每 RTT 加多少？ | **翻倍**（每收到 1 个 ACK 加 1 MSS） |
| 8 | 拥塞避免阶段每收到一个 ACK 加 1 吗？ | **不是**。是**每个 RTT 加 1 MSS**（每 ACK 加 $MSS × MSS/cwnd$） |
| 9 | cwnd 达到 ssthresh 时发生什么？ | **从慢启动转入拥塞避免**，增长由指数变线性 |
| 10 | 超时后 cwnd 变成多少？ | **1 MSS**，且进入**慢启动** |
| 11 | 收到 3 个冗余 ACK 后 cwnd 变成多少？ | **ssthresh（= 原 cwnd 的一半）**，且进入**拥塞避免**（快恢复），**不回 1、不慢启动** |
| 12 | 快重传会改变窗口吗？ | **不会**。快重传只负责**立即重传**；改窗口的是**快恢复** |
| 13 | "3 个冗余 ACK"是 3 个还是 4 个 ACK？ | 是 **3 个重复的**（即除原始 ACK 外又收到 3 个相同的），总共 4 个相同 ACK |

### 8.3 滑动窗口协议类

| # | 易错点 | 正解 |
|:-:|:-------|:-----|
| 14 | 链路层窗口和 TCP 窗口单位相同吗？ | **不同**。链路层单位是**帧**，TCP 单位是**字节** |
| 15 | GBN 的发送窗口能开到 $2^n$ 吗？ | **不能**，上限是 $2^n - 1$（否则序号回绕无法区分新旧帧） |
| 16 | SR 的发送窗口上限？ | $2^{n-1}$，且 $W_T = W_R$（约束是 $W_T + W_R ≤ 2^n$） |
| 17 | GBN 和 SR 谁用累积确认？ | **GBN 累积确认**（一个 ACK 确认之前所有）；**SR 逐个独立确认** |
| 18 | GBN 出错要重传几帧？ | **出错帧及其后所有已发帧全部重传**（回退 N 帧）；SR **只重传出错那一帧** |
| 19 | SR 窗口更大所以一定更好吗？ | 不一定。SR 接收方需**乱序缓存**，实现复杂；GBN 接收方只需 1 帧缓存 |

### 8.4 流量整形与 QoS 类

| # | 易错点 | 正解 |
|:-:|:-------|:-----|
| 20 | 漏桶允许突发吗？ | **不允许**，输出速率**恒定**。允许突发的是**令牌桶** |
| 21 | 令牌桶最大突发量等于桶容量 $b$ 吗？ | **不等于**，是 $\dfrac{b·M}{M-r}$（突发期间令牌还在持续生成） |
| 22 | IntServ 为什么没普及？ | **每流一份状态**导致路由器状态爆炸，**不可扩展**；且需要 RSVP 信令。DiffServ 按类聚合才可扩展 |
| 23 | RED 的目的是减少丢包吗？ | **不是**，是**打散丢包的时间分布**以打破**全局同步** |
| 24 | 缓冲区越大网络越好吗？ | **不是**。缓冲区过大会导致 **Bufferbloat**：排队时延暴涨、RTT 失真、交互体验崩溃 |

### 8.5 记忆口诀

> [!tip] 七句速记
> - **保护对象**：流控保**收端**，拥塞保**网络**
> - **窗口取值**：$\min(rwnd, cwnd)$，取小的
> - **变量归属**：rwnd **公开**（报文中传），cwnd **私有**（只在发送方）
> - **两种丢包**：超时回 **1** 走**慢启动**；三冗余 ACK 回**一半**走**拥塞避免**
> - **慢启动不慢**：起点低，增长是**指数**
> - **整形两桶**：漏桶**恒速不突发**，令牌桶**可突发**
> - **AIMD**：加性增（每 RTT +1），乘性减（× 1/2）
