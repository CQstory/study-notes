# 第五章——传输层

## 5.1 传输层功能与服务

### 5.1.1 传输层的地位

- 传输层是**面向通信部分的最高层**，也是**用户功能中的最低层**
- 传输层提供**进程到进程**（端到端）的通信服务
- 网络层提供**主机到主机**的通信服务

### 5.1.2 传输层的功能

| 功能 | 说明 |
|------|------|
| **进程到进程通信** | 通过端口号标识不同的应用进程 |
| **复用和分用** | 复用：多个应用进程可通过同一个传输层协议发送数据；分用：传输层将数据正确交付给对应的应用进程 |
| **差错检测** | 对首部和数据部分进行校验（TCP和UDP都有校验和） |
| **流量控制** | 控制发送速率，防止接收方缓冲区溢出 |
| **拥塞控制** | 防止过多数据注入网络导致网络过载（仅TCP） |
| **可靠传输** | 保证数据无差错、不丢失、不重复、按序到达（仅TCP） |

### 5.1.3 端口号

- 端口号用于标识主机中的不同应用进程
- 端口号长度为16位，范围为 0~65535

| 端口类型 | 范围 | 说明 |
|---------|------|------|
| **熟知端口** | 0~1023 | 分配给最重要网络应用（如HTTP=80，FTP=21，SSH=22） |
| **登记端口** | 1024~49151 | 分配给没有熟知端口号的应用程序 |
| **动态/短暂端口** | 49152~65535 | 客户端临时使用的端口 |

#### 常见端口号

| 协议 | 端口号 | 说明 |
|------|--------|------|
| FTP | 21 | 文件传输协议（控制连接） |
| FTP数据 | 20 | 文件传输协议（数据连接） |
| SSH | 22 | 安全远程登录 |
| HTTP | 80 | 超文本传输协议 |
| HTTPS | 443 | 安全HTTP |
| DNS | 53 | 域名系统 |
| SMTP | 25 | 简单邮件传输协议 |
| POP3 | 110 | 邮局协议 |
| TELNET | 23 | 远程终端协议 |

## 5.2 UDP协议

### 5.2.1 UDP首部格式

UDP首部仅8字节，非常简洁：

```
 0       7 8      15 16    31
 +--------+--------+--------+--------+
 |   源端口号     |  目的端口号     |
 +--------+--------+--------+--------+
 |    长度        |   校验和        |
 +--------+--------+--------+--------+
 |           数据                     |
 +-----------------------------------+
```

| 字段 | 长度 | 说明 |
|------|------|------|
| **源端口号** | 16位 | 发送方进程的端口号（可选） |
| **目的端口号** | 16位 | 接收方进程的端口号 |
| **长度** | 16位 | UDP首部+数据的总长度（最小8字节） |
| **校验和** | 16位 | 检测首部和数据是否有错（可选，IPv4中可选，IPv6中必选） |

### 5.2.2 UDP的特点

| 特点 | 说明 |
|------|------|
| **无连接** | 发送前不需要建立连接 |
| **不可靠** | 不保证数据可靠交付，使用"尽最大努力交付" |
| **面向报文** | 对应用层交付的报文既不合并也不拆分，保留原边界 |
| **无拥塞控制** | 即使网络拥塞也不会降低发送速率 |
| **首部开销小** | 仅8字节 |
| **支持一对一、一对多、多对多** | 支持单播、多播和广播 |

### 5.2.3 UDP校验和与伪首部

#### 伪首部

UDP校验和计算时，需要在UDP数据报前添加一个**12字节的伪首部**。伪首部仅在计算校验和时使用，**不真正发送**，用于验证数据报是否到达了正确的目的IP和端口。

```
 0                               31
 +-------------------------------+
 |        源IP地址（4B）          |
 +-------------------------------+
 |       目的IP地址（4B）         |
 +-------------------------------+
 |  全零(1B) | 协议(1B) | UDP长度(2B) |
 +-------------------------------+
 |       UDP首部 + 数据           |
 +-------------------------------+
```

| 伪首部字段 | 长度 | 说明 |
|-----------|------|------|
| 源IP地址 | 4字节 | 来自IP首部 |
| 目的IP地址 | 4字节 | 来自IP首部 |
| 全零 | 1字节 | 填充 |
| 协议 | 1字节 | UDP的协议号为17 |
| UDP长度 | 2字节 | UDP首部+数据的总长度 |

#### 校验和计算过程

1. 将伪首部 + UDP首部 + 数据看作一连串的**16位字**
2. 若数据长度为奇数字节，在末尾填充一个全零字节（不发送）
3. 对所有16位字进行**二进制反码求和**
4. 取结果的反码作为校验和
5. 接收方用相同方法计算（含校验和字段），结果应全为1

> [!example] UDP校验和计算示例
> 假设UDP数据报中数据部分只有2字节：`0x03F5`
> - 源IP: 192.168.1.1 → 0xC0A8 0x0101
> - 目的IP: 192.168.1.2 → 0xC0A8 0x0102
> - 协议: 17 → 0x0011
> - 源端口: 3000 → 0x0BB8
> - 目的端口: 53 → 0x0035
> - 长度: 8(首部) + 2(数据) = 10 → 0x000A
>
> 伪首部 + UDP首部 + 数据的16位字：
> `0xC0A8, 0x0101, 0xC0A8, 0x0102, 0x0011, 0x000A, 0x0BB8, 0x0035, 0x000A, 0x03F5`
>
> 求和 → 取反码 → 得到校验和

> [!important] 伪首部核心考点
> - 伪首部**不实际传输**，仅用于校验和计算
> - 伪首部包含IP地址，使UDP校验和能检测数据报是否到达正确的目的IP
> - TCP校验和同样使用伪首部，协议字段为6
> - IPv4中UDP校验和**可选**（全0表示不计算），IPv6中**必选**

### 5.2.4 UDP的适用场景

- 实时应用（如视频会议、IP电话）：对延迟敏感，可容忍少量丢包
- 简单请求-响应应用（如DNS、SNMP）
- 多播/广播应用
- 不需要可靠传输的场景

### 5.2.5 UDP vs TCP对比

| 对比项 | UDP | TCP |
|--------|-----|-----|
| 连接方式 | 无连接 | 面向连接（三次握手） |
| 可靠性 | 不可靠（尽最大努力交付） | 可靠（保证交付） |
| 传输单位 | 面向报文（保留报文边界） | 面向字节流（无边界） |
| 首部开销 | 8字节 | 最小20字节 |
| 流量控制 | 无 | 有（滑动窗口） |
| 拥塞控制 | 无 | 有（慢开始/拥塞避免/快重传/快恢复） |
| 通信方式 | 一对一、一对多、多对多 | 仅一对一 |
| 序号/确认 | 无 | 有 |
| 重传机制 | 无 | 有（超时重传、快重传） |
| 校验和 | 可选（IPv4）/必选（IPv6） | 必选 |
| 适用场景 | 实时应用、DNS、SNMP | HTTP、FTP、SMTP |

### 5.2.6 UDP应用层补充可靠性与典型选例

UDP 本身不做排序、不做重传、不做流控。如果应用需要这些能力，必须**应用层自己实现**：

| 应用层手段 | 做什么 | 示例 |
|-----------|--------|------|
| 应用层序号 | 检测丢包/乱序 | RTP 时间戳+序号 |
| 应用层超时重传 | 没收到就重新请求 | DNS 查询超时重发 |
| 应用层确认 | 收到回 ACK | TFTP（每包等ACK） |
| 跳帧 + 丢弃迟到包 | 实时性优先 | 微信视频、IP电话 |

> [!example] 实时视频（微信视频）的 UDP 丢包策略
> 场景：发送帧 1~100，其中 11~20 丢失。
>
> ```
> 正在播第10帧，期望第11帧
>   │
>   ├─ 短暂等待（抖动缓冲区，约50~100ms）
>   │   ├─ 等到 11~20 → 正常续播
>   │   └─ 没等到（真丢了） → 跳到下一个可用帧（如21）
>   │
>   └─ 若帧15迟到（此时已播过21）→ seq < 播放位置 → **直接丢弃**
> ```
>
> 关键区别（vs TCP）：
> - TCP：不连续就不交付，等缺口填上
> - 实时UDP：**等一会就跳**，迟到的老序号直接扔
> - 原因：实时通话不能倒带，超过200ms延迟人就感觉卡

> [!important] DNS 的 UDP→TCP 切换（408 考点）
> - DNS 默认用 UDP（端口53），快，一次一问一答
> - 当响应超过 **512 字节**（RFC 1035 规定的 UDP DNS 上限） → 回退到 **TCP**
> - 区域传输（AXFR）：数据量巨大 → **永远走 TCP**
> - 选择标准：**少量快问快答用 UDP，大量可靠传输用 TCP**

## 5.3 TCP协议

### 5.3.1 TCP首部格式

TCP首部固定部分为20字节，选项部分可变：

```
 0               16              31
 +-------+-------+---------------+
 |    源端口号                   |
 +-------------------------------+
 |    目的端口号                 |
 +-------------------------------+
 |          序号                 |
 +-------------------------------+
 |        确认号                 |
 +-------+-------+---------------+
 |首部长度| 保留  | 标志位        |
 | (4位) | (6位) |URG|ACK|PSH|RST|SYN|FIN|
 +-------+-------+---------------+
 |        窗口大小               |
 +-------------------------------+
 |        校验和                 |
 +-------------------------------+
 |        紧急指针               |
 +-------------------------------+
 |        选项（可变长度）         |
 +-------------------------------+
 |           数据                 |
 +-------------------------------+
```

| 字段 | 长度 | 说明 |
|------|------|------|
| **源端口号** | 16位 | 发送方进程端口号 |
| **目的端口号** | 16位 | 接收方进程端口号 |
| **序号** | 32位 | 本报文段数据第一个字节的编号 |
| **确认号** | 32位 | 期望收到对方下一个报文段第一个字节的编号 |
| **首部长度** | 4位 | 以4字节为单位，最小5（20字节），最大15（60字节） |
| **URG** | 1位 | 紧急指针有效 |
| **ACK** | 1位 | 确认号有效（连接建立后始终为1） |
| **PSH** | 1位 | 接收方应尽快交付给应用层 |
| **RST** | 1位 | 重置连接 |
| **SYN** | 1位 | 同步序号，用于建立连接 |
| **FIN** | 1位 | 发送方完成发送，用于释放连接 |
| **窗口大小** | 16位 | 接收方的接收窗口大小（用于流量控制） |
| **校验和** | 16位 | 校验首部和数据 |
| **紧急指针** | 16位 | 紧急数据的末尾在报文段中的位置 |

### 5.3.2 TCP的特点

| 特点 | 说明 |
|------|------|
| **面向连接** | 通信前需要建立连接（三次握手） |
| **可靠传输** | 保证数据无差错、不丢失、不重复、按序到达 |
| **面向字节流** | 将应用层数据视为无结构的字节流 |
| **全双工通信** | 双方可以同时发送和接收数据 |
| **点对点通信** | 仅支持一对一通信 |
| **有拥塞控制** | 根据网络状况调整发送速率 |

### 5.3.3 TCP选项字段

TCP首部的选项部分（可变长度，以4字节为单位对齐）支持多种扩展功能：

| 选项 | 类型值 | 长度 | 说明 |
|------|--------|------|------|
| **MSS（最大报文段长度）** | 2 | 4字节 | 协商每个TCP报文段中数据部分的最大长度，仅在SYN报文段中使用 |
| **窗口扩大选项** | 3 | 3字节 | 将窗口大小字段从16位扩大到最多32位，用于高速网络 |
| **时间戳选项** | 8 | 10字节 | 计算RTT、防止序号回绕（PAWS） |
| **SACK（选择确认）** | 5 | 可变 | 告知发送方已收到的数据块范围，减少不必要的重传 |
| **窗口扩大因子** | — | — | 窗口大小 = 首部窗口值 × $2^{移位数}$ |

> [!important] MSS与MTU的关系
> - **MSS**（Maximum Segment Size）是TCP数据部分的最大长度
> - MSS = MTU - IP首部(20) - TCP首部(20) = MTU - 40
> - 以太网MTU=1500，因此典型MSS = 1500 - 40 = **1460字节**
> - MSS仅在建立连接时通过SYN报文段协商，取双方MSS的较小值
> - MSS是**避免IP分片**的重要机制

> [!tip] 序号回绕问题
> - TCP序号为32位，最大值为 $2^{32} - 1 = 4,294,967,295$
> - 在高速网络中，序号可能很快用完一圈回到0
> - 使用**时间戳选项（PAWS）**可以区分新旧报文段，防止序号回绕导致的错误

## 5.4 TCP连接管理

### 5.4.1 三次握手（建立连接）

```
客户端                              服务器
  |                                    |
  |  SYN=1, seq=x                     |  (CLOSED → LISTEN)
  |  -------------------------------->|
  |                                    |  (LISTEN → SYN-RCVD)
  |  SYN=1, ACK=1, seq=y, ack=x+1    |
  |  <--------------------------------|
  |  (SYN-SENT → ESTABLISHED)          |  (SYN-RCVD → ESTABLISHED)
  |  ACK=1, seq=x+1, ack=y+1         |
  |  -------------------------------->|
  |                                    |
  |          连接建立完成               |
```

#### 三次握手详细说明

| 步骤 | 方向 | 标志位 | 说明 |
|------|------|--------|------|
| 第一次 | 客户端→服务器 | SYN=1, seq=x | 客户端请求建立连接，发送自己的初始序号x |
| 第二次 | 服务器→客户端 | SYN=1, ACK=1, seq=y, ack=x+1 | 服务器确认客户端的请求，同时发送自己的SYN和初始序号y |
| 第三次 | 客户端→服务器 | ACK=1, seq=x+1, ack=y+1 | 客户端确认服务器的SYN |

> [!tip] 为什么需要三次握手？
> 1. 防止已失效的连接请求报文突然到达服务器，造成资源浪费
> 2. 确认双方的发送和接收能力都正常
> 3. 同步双方的初始序号

> [!warning] 易错：第一次 SYN 没有 ACK
> - 第一次握手只有 `SYN=1, seq=x`，**没有 ACK 标志、没有确认号**
> - 原因：此时客户端尚未收到服务器的任何信息，无东西可确认
> - TCP 头中 ACK 字段（32位）虽然物理存在，但 **ACK 标志位=0 时确认号无意义**
> - 考试简写可以省略 ack，不要写成 `ack=0` 还带 ACK 标志

### 5.4.2 SYN泛洪攻击与防御

#### SYN泛洪攻击原理

- 攻击者伪造大量源IP地址，向服务器发送**SYN报文段**
- 服务器为每个SYN分配资源并回复SYN+ACK，等待第三次握手
- 攻击者不会完成第三次握手，服务器中大量连接处于**SYN-RCVD**状态
- 最终服务器资源耗尽，无法为正常用户提供服务

#### 防御措施

| 防御方法 | 说明 |
|----------|------|
| **SYN Cookie** | 服务器不预分配资源，将状态编码在SYN+ACK的初始序号中，收到合法ACK后才分配资源 |
| **减小SYN队列超时时间** | 加速清理半开连接 |
| **SYN Proxy** | 防火墙代理三次握手，建立成功后才转发给服务器 |
| **限制半开连接数** | 超过阈值后拒绝新的SYN请求 |

> [!important] SYN Cookie原理
> - 服务器不分配资源，而是将 `(源IP, 源端口, 时间戳, MSS)` 编码为初始序号返回
> - 收到第三次握手的ACK时，验证ACK号是否等于 `服务器初始序号 + 1`
> - 验证通过才真正分配连接资源，避免被攻击消耗资源

### 5.4.3 四次挥手（释放连接）

```
客户端                              服务器
  |                                    |
  |  FIN=1, seq=u                     |  (ESTABLISHED)
  |  -------------------------------->|  (ESTABLISHED → CLOSE-WAIT)
  |  (ESTABLISHED → FIN-WAIT-1)       |
  |  ACK=1, seq=v, ack=u+1           |
  |  <--------------------------------|  (CLOSE-WAIT → LAST-ACK)
  |  (FIN-WAIT-1 → FIN-WAIT-2)       |
  |                                    |  (服务器继续发送未完成的数据)
  |  FIN=1, ACK=1, seq=w, ack=u+1    |
  |  <--------------------------------|
  |  (FIN-WAIT-2 → TIME-WAIT)         |
  |  ACK=1, seq=u+1, ack=w+1         |
  |  -------------------------------->|
  |                                    |  (LAST-ACK → CLOSED)
  |  等待2MSL后                        |
  |  (TIME-WAIT → CLOSED)             |
```

#### 四次挥手详细说明

| 步骤 | 方向 | 标志位 | 说明 |
|------|------|--------|------|
| 第一次 | 客户端→服务器 | FIN=1, seq=u | 客户端请求关闭连接（半关闭） |
| 第二次 | 服务器→客户端 | ACK=1, seq=v, ack=u+1 | 服务器确认收到关闭请求 |
| 第三次 | 服务器→客户端 | FIN=1, ACK=1, seq=w, ack=u+1 | 服务器数据发送完毕，请求关闭连接 |
| 第四次 | 客户端→服务器 | ACK=1, seq=u+1, ack=w+1 | 客户端确认服务器的关闭请求 |

> [!tip] 建立3次 vs 释放4次：为什么差一次？
> - **建立时可以合并**：服务器的 SYN 和 ACK 恰好同时发生 → `SYN+ACK` 合为一个段 → 3次
> - **释放时不能合并**：服务器收到 FIN 后立即 ACK（第2次），但自己可能还有数据没发完，FIN 必须等到数据发完才发（第3次）→ ACK 和 FIN 之间有间隔 → 4次
> - 口诀：**建立合并（同时同意），释放不合并（各关各的）**

### 5.4.4 TCP连接状态转换图

```
                    +-----------+
            passive OPEN |  CLOSED   | passive OPEN
            ------------>|           | <------------
                         |           |
               active OPEN|           | passive OPEN
               ---------->|  LISTEN   | ----------
                         |           |
              SYN sent   |           | SYN received
              ---------->| SYN-RCVD  | <----------
                         |           |
              SYN+ACK    |           |
              <----------|           |
                         |           |
              ACK        |           |
              ---------->| ESTABLISHED| <----------
                         |           |
              FIN        |           |
              ---------->| CLOSE-WAIT| <----------
                         |           |
              ACK        |           | FIN
              <----------| LAST-ACK  | <----------
                         |           |
              FIN        |           |
              <----------| FIN-WAIT-2|
                         |           |
              ACK        |           |
              ---------->| TIME-WAIT |
                         |           |
              2MSL       |           |
              ---------->|  CLOSED   |
                         +-----------+
```

#### 各状态说明

| 状态 | 说明 |
|------|------|
| **CLOSED** | 初始状态，无连接 |
| **LISTEN** | 服务器等待连接请求 |
| **SYN-SENT** | 客户端已发送SYN，等待确认 |
| **SYN-RCVD** | 服务器已收到SYN并发送SYN+ACK，等待ACK |
| **ESTABLISHED** | 连接已建立，可以传输数据 |
| **FIN-WAIT-1** | 主动关闭方已发送FIN，等待ACK |
| **FIN-WAIT-2** | 主动关闭方已收到ACK，等待对方的FIN |
| **CLOSE-WAIT** | 被动关闭方已收到FIN并发送ACK，等待应用层关闭 |
| **LAST-ACK** | 被动关闭方已发送FIN，等待ACK |
| **TIME-WAIT** | 主动关闭方已发送ACK，等待2MSL后关闭 |

> [!tip] TIME-WAIT状态
> - 主动关闭方进入TIME-WAIT状态后等待 **2MSL**（Maximum Segment Lifetime，最长报文段寿命）
> - 等待2MSL的原因：
>   1. 确保最后一个ACK能到达对方（若丢失可重传）
>   2. 等待网络中残留的报文段过期，避免影响新连接

## 5.5 TCP流量控制

> [!note] 横向对比入口
> TCP 流量控制（rwnd）与拥塞控制（cwnd）的**十一维辨析**、rwnd 与 cwnd 的**公开/私有**之别、**糊涂窗口综合征**（SWS）与 Nagle / Clark 方案、与数据链路层 SW/GBN/SR 的**窗口单位陷阱**（字节 vs 帧），见 [[专题02——流量控制与拥塞控制]] §2、§3.1、§3.2。

### 5.5.1 滑动窗口机制

- TCP使用**滑动窗口**实现流量控制
- 接收方通过**窗口大小**字段告知发送方自己的接收缓冲区剩余空间
- 发送方的发送窗口不能超过接收方通告的窗口大小

#### 滑动窗口示意图

```
发送方：
  [已确认] [发送窗口（可发送但未确认）] [不可发送]
  ←─────── 已发送未确认 ──────→
  ←──────────── 发送窗口 ────────────→

接收方：
  [已确认交付] [接收窗口（可接收）] [不可接收]
```

#### 窗口变化规则

- 接收方有足够缓冲区时，通告较大窗口
- 接收方缓冲区快满时，通告较小窗口（甚至0）
- 发送方收到窗口为0时，必须停止发送（**零窗口探测**）

### 5.5.2 零窗口探测

- 当接收方通告窗口为0时，发送方启动**持续计时器**
- 计时器超时后，发送方发送**零窗口探测报文**（仅1字节）
- 接收方回复包含当前窗口大小的确认
- 防止死锁（防止接收方发送的窗口更新报文丢失导致双方僵持）

## 5.6 TCP拥塞控制

### 5.6.1 拥塞控制基本概念

- **拥塞控制**与**流量控制**的区别：
  - 流量控制：控制发送方与接收方之间的速率（端到端）
  - 拥塞控制：控制整个网络的负载（全局性）
- TCP通过**拥塞窗口（cwnd）**来控制发送速率
- 发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)

> [!warning] 关键补充：cwnd 不在报文中传输
> **cwnd 是发送方的本地变量**，从不出现在 TCP 报文里，接收方完全不知道它的值；而 **rwnd 是接收方通过首部窗口字段显式通告**的。一个私有、一个公开 —— 这是选择题高频陷阱。
>
> 另外注意：**「慢启动」其实是指数增长**（每 RTT 翻倍），名字里的「慢」指的是**起点低**（从 1 MSS 开始），不是增长慢。

> [!note] 深化入口
> 四大算法的**精确增量规则**、**超时 vs 3 个冗余 ACK 的差异化反应**（超时回 1 走慢启动 / 快恢复回一半走拥塞避免）、**25 轮 cwnd 逐 RTT 演算表**、状态机图、Mathis 公式与长肥管道、**现代算法（CUBIC / BBR / QUIC）**、**漏桶与令牌桶**、IntServ/DiffServ、RED/CoDel 与全局同步、拥塞崩溃，见 [[专题02——流量控制与拥塞控制]] §3.3–3.6、§4–§7。

### 5.6.2 四种拥塞控制算法

#### 1. 慢开始（Slow Start）

- 连接建立后，cwnd = 1（1个MSS）
- 每收到一个ACK，cwnd加1（即每个RTT，cwnd**翻倍增长**）
- 当cwnd达到**慢开始门限（ssthresh）**时，转为拥塞避免
- 发生超时（拥塞）时：
  - ssthresh = cwnd / 2
  - cwnd = 1
  - 重新慢开始

#### 2. 拥塞避免（Congestion Avoidance）

- cwnd达到ssthresh后，每个RTT只将cwnd**加1**（线性增长）
- 发生超时时：
  - ssthresh = cwnd / 2
  - cwnd = 1
  - 重新慢开始

#### 3. 快重传（Fast Retransmit）

- 接收方每收到一个失序报文段，就立即发送**重复确认**
- 发送方收到**3个重复确认**时，立即重传丢失的报文段（不等超时）

#### 4. 快恢复（Fast Recovery）

- 与快重传配合使用
- 收到3个重复确认时：
  - ssthresh = cwnd / 2
  - cwnd = ssthresh（不是设为1）
  - 直接进入拥塞避免（不是慢开始）

### 5.6.3 拥塞窗口变化过程示例

>

## 5.7 TCP可靠传输

### 5.7.1 可靠传输的机制概述

TCP通过以下机制实现可靠传输：

| 机制 | 说明 |
|------|------|
| **序号与确认** | 每个字节编号，接收方确认已收到的数据 |
| **超时重传** | 发送后未收到确认则重传 |
| **快重传** | 收到3个重复确认则立即重传 |
| **流量控制** | 滑动窗口控制发送速率 |
| **校验和** | 检测数据传输中的差错 |
| **按序交付** | 接收方按序号重组后交付上层 |

### 5.7.2 序号与确认号

- **序号**：本报文段数据第一个字节在字节流中的编号
- **确认号**：期望收到的下一个字节的编号
- TCP采用**累积确认**：确认号n表示n之前的所有数据都已正确收到

> [!example] 序号与确认号计算示例
> 主机A发送序号为201、数据长度为200字节的报文段。
> 主机B正确收到后回复确认号 = 201 + 200 = 401。
> 表示B期望收到序号从401开始的数据。
>
> 若A再发送序号401、数据长度300字节的报文段：
> B正确收到后回复确认号 = 401 + 300 = 701。
>
> 特殊情况：
> - SYN报文段消耗一个序号（但不携带数据）
> - FIN报文段消耗一个序号（但不携带数据）
> - ACK报文段不消耗序号
> - 建立连接时，A的初始序号seq=x，则第一个数据报文段的序号=x+1

> [!important] SYN/FIN消耗序号
> - SYN和FIN虽然不携带数据，但各消耗一个序号
> - 因为SYN和FIN需要可靠传输（需要被确认）
> - ACK报文段不携带数据也不消耗序号

### 5.7.3 累积确认与GBN/SR的关系

TCP的可靠传输机制结合了GBN和SR的特点：

| 特性 | GBN | SR | TCP |
|------|-----|----|----|
| 确认方式 | 累积确认 | 逐帧确认 | 累积确认（默认）+ SACK（可选） |
| 重传范围 | 出错帧及后续所有 | 仅出错帧 | 默认重传（超时重传所有未确认），快重传仅重传丢失段 |
| 接收缓存 | 不缓存乱序帧 | 缓存乱序帧 | **缓存乱序到达的报文段** |
| 接收窗口 | 1 | >1 | >1 |

- TCP默认使用**累积确认**，类似于GBN
- 但TCP接收方会**缓存乱序到达的报文段**，类似于SR
- 启用SACK选项后，发送方可以知道哪些段已收到，只重传缺失的段，更接近SR

### 5.7.4 乱序段处理完整交互示例

> [!example] 场景：发送 [1][2][3][4][5]，段1丢失
>
> **接收方视角**（假设每段1字节，序号从1开始）：
>
> | 收到 | 动作 | 发出的ACK |
> |------|------|----------|
> | 段2 (seq=2) | 缺段1 → 暂存乱序区 | ACK=1（期望段1） |
> | 段3 (seq=3) | 仍缺段1 → 暂存 | ACK=1（dupACK） |
> | 段4 (seq=4) | 仍缺段1 → 暂存 | ACK=1（dupACK） |
> | 段5 (seq=5) | 仍缺段1 → 暂存 | ACK=1（dupACK） |
> | 段1 (seq=1)（重传到达） | **缺口填补！** 1-2-3-4-5连续 | ACK=6（一口气确认全部） |
>
> **发送方视角**：
> 1. 收到3个 `ACK=1`（dupACK） → **快重传**段1
> 2. 若没凑齐3个dupACK就超时 → **超时重传**段1
> 3. 重传后段1到达接收方 → 所有段连续交付 → ACK跳进至6
>
> **关键规则**：
> - 乱序段**只暂存不交付**——接收方绝不上交不连续的数据
> - ACK号**停在缺口处不动**——表示"还在等这个号"
> - 已缓存的乱序段**不会被后续段挤掉**——除非窗口满
> - 窗口满时新到的段**直接丢弃**（不覆盖已有缓存）

### 5.7.5 超时重传

- 发送方发送报文段后启动**重传计时器**
- 若在超时前收到确认，则取消计时器
- 若超时未收到确认，则重传该报文段

#### 超时重传时间（RTO）计算

- TCP采用**自适应算法**动态计算超时重传时间
- 首先测量**加权平均往返时间（RTT_S）**：
  $$RTT_S = (1 - \alpha) \times RTT_S + \alpha \times RTT_{new}$$
  其中 $\alpha$ 推荐值为 0.125
- 然后计算**RTT偏差（RTT_D）**：
  $$RTT_D = (1 - \beta) \times RTT_D + \beta \times |RTT_S - RTT_{new}|$$
  其中 $\beta$ 推荐值为 0.25
- 最终超时重传时间：
  $$RTO = RTT_S + 4 \times RTT_D$$

> [!warning] Karn算法
> - 当一个报文段被重传时，其RTT样本**不应**用于更新RTT_S
> - 因为无法确认收到的ACK是对原始报文还是对重传报文的确认
> - 这就是**Karn算法**：忽略重传报文段的RTT测量值

### 5.7.6 选择确认SACK

- TCP首部的确认号是累积确认，无法确认乱序到达的报文段
- **SACK（Selective ACK）**选项允许接收方告知发送方哪些数据已正确收到
- 使用SACK选项需要在TCP首部中添加选项字段
- SACK通过左右边界描述已收到的数据块

> [!example] SACK示例
> 发送方发送序号1~1000的数据（5个200字节的段），段2和段4丢失：
> - 接收方收到：段1(1-200), 段3(401-600), 段5(801-1000)
> - 累积确认：ACK=201（期望收到段2）
> - SACK选项：[401-600], [801-1000]
> - 发送方知道只需重传段2(201-400)和段4(601-800)，不需重传段3和段5

### 5.7.7 TCP优化机制

#### Nagle算法

- **问题**：大量小分组（如1字节）会造成网络效率低下（首部开销占比大）
- **Nagle算法**：发送方将小数据缓存，积攒到足够大或收到前一个确认后才发送
- 规则：
  1. 若发送窗口 ≥ MSS 且数据 ≥ MSS，立即发送
  2. 若数据 < MSS 且有未确认数据，缓存不发送
  3. 若数据 < MSS 但所有已发数据都已确认，立即发送

> [!tip] Nagle算法的适用场景
> - 适用于交互式应用（如Telnet），减少小分组数量
> - 不适用于实时性要求高的应用（会增加延迟）
> - 可通过设置TCP_NODELAY选项禁用

#### 延迟确认（Delayed ACK）

- 接收方收到数据后不立即发送ACK，等待一小段时间（通常200ms）
- 若期间有数据需要发送，则将ACK**捎带**在数据报文段中
- 若等待期间有新数据到达，则立即发送ACK
- 目的：减少纯ACK报文段的数量，提高效率

#### 糊涂窗口综合症（Silly Window Syndrome）

- **问题**：接收方缓冲区快满时通告很小的窗口，发送方发送很小的数据，导致效率极低
- **接收方解决**：Clark方案 — 只有当窗口大小 ≥ min(MSS, 缓冲区空间的一半)时才通告非零窗口
- **发送方解决**：Nagle算法 — 不发送小于MSS的数据

> [!important] Nagle与延迟确认的冲突
> - Nagle算法要求发送方等待ACK后再发小数据
> - 延迟确认要求接收方延迟发送ACK
> - 两者同时使用会导致**额外延迟**
> - 解决方案：禁用Nagle算法或禁用延迟确认

## 5.8 TCP流量控制计算示例

### 5.8.1 滑动窗口交互过程

> [!example] 流量控制完整示例
> 假设A向B发送数据，B的接收缓存总大小为400字节，初始rwnd=400。
>
> | 步骤 | A发送 | B收到后 | B通告窗口 | 说明 |
> |------|-------|---------|-----------|------|
> | 1 | seq=1, 数据100B | 已收100B，缓存剩300B | rwnd=300, ack=101 | — |
> | 2 | seq=101, 数据100B | 已收200B，缓存剩200B | rwnd=200, ack=201 | — |
> | 3 | seq=201, 数据100B | 已收300B，缓存剩100B | rwnd=100, ack=301 | — |
> | 4 | seq=301, 数据100B | 已收400B，缓存满 | rwnd=0, ack=401 | **窗口为0，A停止发送** |
> | — | A启动持续计时器 | — | — | 等待窗口更新 |
> | 5 | 零窗口探测(1B) | B读取200B，缓存剩200B | rwnd=200 | **窗口更新** |
> | 6 | seq=401, 继续发送 | — | — | A恢复发送 |

### 5.8.2 发送窗口的确定

$$发送窗口 = \min(接收窗口\ rwnd,\ 拥塞窗口\ cwnd)$$

| 情况 | 发送窗口 | 说明 |
|------|----------|------|
| rwnd < cwnd | rwnd | 接收方限制（流量控制） |
| rwnd > cwnd | cwnd | 网络限制（拥塞控制） |
| rwnd = 0 | 0 | 接收方缓存满，停止发送 |

> [!important] 流量控制 vs 拥塞控制
> - **流量控制**：rwnd由接收方通过窗口字段通告，防止接收方溢出
> - **拥塞控制**：cwnd由发送方根据网络状况自行调整，防止网络过载
> - 实际发送窗口取两者**较小值**

## 5.9 TCP定时器

TCP使用多种定时器来保证连接的可靠性和活跃性：

| 定时器 | 作用 | 触发条件 | 超时动作 |
|--------|------|----------|----------|
| **重传计时器** | 确保丢失的报文段被重传 | 发送报文段后启动 | 重传未确认的报文段 |
| **持续计时器** | 解决零窗口死锁 | 收到rwnd=0时启动 | 发送零窗口探测报文 |
| **保活计时器** | 检测连接是否仍然活跃 | 连接空闲时启动（可选） | 探测对方是否存活 |
| **时间等待计时器** | 确保连接正常关闭 | 主动关闭方进入TIME-WAIT | 等待2MSL后关闭连接 |

### 5.9.1 重传计时器

- 每个已发送但未确认的报文段启动一个重传计时器
- 超时时间RTO由自适应算法计算（见5.7.5）
- 收到确认后取消对应计时器
- 超时则重传报文段，并将RTO**加倍**（退避策略），避免连续重传加剧拥塞

> [!important] 重传退避策略
> - 每次重传后，RTO = 2 × RTO（指数退避）
> - 最多退避64次后放弃，关闭连接
> - 退避期间不更新RTT_S（Karn算法）

### 5.9.2 持续计时器

- 当接收方通告窗口为0时，发送方启动持续计时器
- 超时后发送**零窗口探测报文**（1字节数据）
- 接收方回复当前窗口大小
- 持续计时器的超时时间也采用**指数退避**（初始值约为500ms，上限约60s）

> [!tip] 为什么需要持续计时器？
> - 接收方缓存腾出空间后，会发送窗口更新报文
> - 但该报文可能丢失，导致发送方一直等待、接收方一直等待 → **死锁**
> - 持续计时器通过主动探测来打破死锁

### 5.9.3 保活计时器

- 用于检测长时间空闲的连接是否仍然有效
- 通常在连接空闲**2小时**后启动
- 发送探测报文，每隔75秒发送一次，连续发送**9次**
- 若9次均无响应，则判定连接已断开，关闭连接

> [!warning] 保活计时器是可选的
> - 保活功能**不是TCP标准的一部分**，而是许多实现的扩展
> - 可能会因短暂网络中断而误断正常连接
> - 408考试中了解概念即可

### 5.9.4 时间等待计时器

- 主动关闭连接的一方进入TIME-WAIT状态后启动
- 持续时间为**2MSL**（Maximum Segment Lifetime）
- MSL通常为30秒~120秒，因此2MSL约为1~4分钟

> [!important] 2MSL的原因
> 1. **保证最后的ACK到达**：若最后一个ACK丢失，被动关闭方会重传FIN，主动关闭方在2MSL内仍可重传ACK
> 2. **使本连接的报文段全部消失**：防止旧连接的延迟报文段影响新连接

## 5.10 TCP半关闭与特殊连接场景

### 5.10.1 TCP半关闭（Half-Close）

TCP提供**半关闭**能力：一方可以停止发送数据但仍然继续接收数据。

```
主机A                                主机B
  |                                    |
  |  FIN=1, seq=u                      |  (A不再发送数据，但仍可接收)
  |  -------------------------------->|  (ESTABLISHED → CLOSE-WAIT)
  |  (FIN-WAIT-1 → FIN-WAIT-2)        |
  |  ACK=1, ack=u+1                   |
  |  <--------------------------------|  (B可以继续发送数据)
  |                                    |
  |  ←—— B继续向A发送数据 ——→          |  (A仍处于FIN-WAIT-2，可接收)
  |                                    |
  |  FIN=1, ACK=1, seq=w              |
  |  <--------------------------------|  (B也完成发送)
  |  (FIN-WAIT-2 → TIME-WAIT)         |
  |  ACK=1, ack=w+1                   |
  |  -------------------------------->|
```

- **半关闭**：A发送FIN后，A不再发送数据，但B仍可向A发送数据
- A进入**FIN-WAIT-2**状态，等待B的FIN
- 直到B也发送FIN，连接才完全关闭

> [!example] 半关闭的应用场景
> - 客户端发送完请求后关闭发送方向，但继续接收服务器响应
> - 如：`shutdown(sock, SHUT_WR)` 系统调用实现半关闭

### 5.10.2 同时打开

两端同时发送SYN，均执行主动打开：

```
主机A                                主机B
  |  SYN=1, seq=x    SYN=1, seq=y    |
  |  -------------->|<--------------|
  |  (SYN-SENT → SYN-RCVD)  (SYN-SENT → SYN-RCVD)  |
  |                                    |
  |  SYN=1, ACK=1, seq=x+1, ack=y+1  |
  |  SYN=1, ACK=1, seq=y+1, ack=x+1  |
  |  -------------->|<--------------|
  |  (→ ESTABLISHED)    (→ ESTABLISHED)|
```

- 双方同时从SYN-SENT转移到SYN-RCVD
- 交换SYN+ACK后双方进入ESTABLISHED
- 最终建立**一条连接**（而非两条）
- 需要交换**9个报文段**（而非三次握手的3个）

### 5.10.3 同时关闭

两端同时发送FIN：

```
主机A                                主机B
  |  FIN=1, seq=u    FIN=1, seq=v    |
  |  -------------->|<--------------|
  |  (→ FIN-WAIT-1)     (→ FIN-WAIT-1)|
  |                                    |
  |  ACK=1, ack=u+1  ACK=1, ack=v+1  |
  |  -------------->|<--------------|
  |  (→ FIN-WAIT-2)     (→ FIN-WAIT-2)|
  |                                    |
  |  (→ CLOSING → TIME-WAIT)         |
  |  双方都进入TIME-WAIT，等待2MSL     |
  |  → CLOSED                          |
```

- 双方都经过 **FIN-WAIT-1 → CLOSING → TIME-WAIT → CLOSED**
- 新增 **CLOSING** 状态：已发送FIN、已收到对方的FIN并发送ACK，等待自己的ACK确认

### 5.10.4 完整TCP状态转换图

```
                        被动OPEN
                      ┌──────────┐
                      │  CLOSED  │←─────────────────────────┐
                      └────┬─────┘                          │
                 主动OPEN │     │ 被动OPEN                    │
                      ┌───▼─────┐                          │
           发送SYN    │ LISTEN  │                          │
         ┌───────────→└────┬────┘                          │
         │                  │ 收到SYN，发送SYN+ACK          │
    ┌────▼─────┐     ┌──────▼──────┐                       │
    │ SYN-SENT │     │  SYN-RCVD   │                       │
    └────┬─────┘     └──────┬──────┘                       │
         │                  │ 收到ACK                       │
         │ 收到SYN+ACK      │                              │
         │ 发送ACK           │                              │
         │           ┌──────▼──────┐                       │
         └──────────→│ ESTABLISHED │←──────────────────────┘
                     └──────┬──────┘  收到SYN+ACK，发送ACK
                      发送FIN │  收到FIN，发送ACK
                    ┌────────▼────────┐
                    │                 │
             ┌──────▼─────┐   ┌───────▼──────┐
             │ FIN-WAIT-1 │   │  CLOSE-WAIT  │
             └──────┬─────┘   └───────┬──────┘
           收到ACK  │          发送FIN │
                    │                 │
             ┌──────▼─────┐   ┌───────▼──────┐
             │ FIN-WAIT-2 │   │   LAST-ACK   │
             └──────┬─────┘   └───────┬──────┘
           收到FIN  │          收到ACK │
           发送ACK  │                 │
                    │                 │
             ┌──────▼─────┐           │
             │ TIME-WAIT  │           │
             └──────┬─────┘           │
             2MSL   │                 │
                    │                 │
             ┌──────▼─────┐   ┌───────▼──────┐
             │   CLOSED   │   │    CLOSED    │
             └────────────┘   └──────────────┘
```

> [!important] 完整状态转换表
> | 当前状态 | 收到的事件 | 动作 | 新状态 |
> |---------|-----------|------|--------|
> | CLOSED | 主动打开 | 发送SYN | SYN-SENT |
> | CLOSED | 被动打开 | — | LISTEN |
> | LISTEN | 收到SYN | 发送SYN+ACK | SYN-RCVD |
> | SYN-SENT | 收到SYN+ACK | 发送ACK | ESTABLISHED |
> | SYN-SENT | 收到SYN（同时打开） | 发送SYN+ACK | SYN-RCVD |
> | SYN-RCVD | 收到ACK | — | ESTABLISHED |
> | ESTABLISHED | 主动关闭 | 发送FIN | FIN-WAIT-1 |
> | ESTABLISHED | 收到FIN | 发送ACK | CLOSE-WAIT |
> | FIN-WAIT-1 | 收到ACK | — | FIN-WAIT-2 |
> | FIN-WAIT-1 | 收到FIN | 发送ACK | CLOSING |
> | FIN-WAIT-1 | 收到FIN+ACK | 发送ACK | TIME-WAIT |
> | FIN-WAIT-2 | 收到FIN | 发送ACK | TIME-WAIT |
> | CLOSE-WAIT | 应用关闭 | 发送FIN | LAST-ACK |
> | LAST-ACK | 收到ACK | — | CLOSED |
> | CLOSING | 收到ACK | — | TIME-WAIT |
> | TIME-WAIT | 2MSL超时 | — | CLOSED |

## 5.11 传输层服务与套接字

### 5.11.1 传输层服务类型

| 服务类型 | 特点 | 代表协议 |
|---------|------|----------|
| **面向连接服务** | 通信前建立连接，通信后释放连接；保证可靠、按序交付 | TCP |
| **无连接服务** | 不需要建立连接；不保证可靠交付；开销小 | UDP |

### 5.11.2 传输服务原语

面向连接的传输服务使用以下基本原语（以Berkeley Socket为例）：

| Socket API | 传输原语 | 说明 |
|-----------|----------|------|
| `socket()` | 创建套接字 | 创建传输端点 |
| `bind()` | 绑定地址 | 将套接字与本地地址(IP:Port)绑定 |
| `listen()` | 监听连接 | 服务器标记套接字为被动监听状态 |
| `accept()` | 接受连接 | 从队列中取出已完成连接，返回新套接字 |
| `connect()` | 请求连接 | 客户端发起连接请求（触发三次握手） |
| `send()` / `recv()` | 数据传输 | 发送/接收数据 |
| `close()` | 关闭连接 | 释放连接（触发四次挥手） |

### 5.11.3 套接字（Socket）

- **套接字** = (IP地址 : 端口号)
- 一个TCP连接由**两个套接字**唯一确定：
  - 连接 = {(IP1:Port1), (IP2:Port2)}
- 套接字是应用层与传输层之间的**接口**

> [!example] 套接字复用
> - 一台服务器可以有多个客户端同时连接
> - 服务器使用同一个熟知端口（如80），但每条连接由不同的客户端IP:Port区分
> - 连接1：{(服务器IP:80), (客户端1IP:50001)}
> - 连接2：{(服务器IP:80), (客户端2IP:50002)}
> - TCP通过**四元组**（源IP, 源端口, 目的IP, 目的端口）唯一标识一条连接

### 5.11.4 复用与分用

| 概念 | 说明 | 示例 |
|------|------|------|
| **复用（Multiplexing）** | 发送方多个应用进程使用同一个传输层协议发送数据 | 多个应用同时通过TCP/UDP发送 |
| **分用（Demultiplexing）** | 接收方传输层将收到的数据正确交付给对应的应用进程 | 根据端口号将数据分发给对应进程 |

```
发送端（复用）：                    接收端（分用）：
┌─────────┐                       ┌─────────┐
│ HTTP(80)│─┐                  ┌──│ HTTP(80)│
├─────────┤ │                  │  ├─────────┤
│ FTP(21) │─┼─→ TCP/UDP ──→───┼──│ FTP(21) │
├─────────┤ │     传输层       │  ├─────────┤
│ DNS(53) │─┘                  └──│ DNS(53) │
└─────────┘                       └─────────┘
```

> [!important] 无连接分用 vs 面向连接分用
> - **UDP分用**：仅根据**目的端口**号将报文交付给对应进程
> - **TCP分用**：根据**四元组**（源IP, 源端口, 目的IP, 目的端口）将报文段交付给对应连接
> - 因此一个UDP套接字只能绑定一个端口，而一个TCP套接字可以对应多个连接（通过accept返回新套接字）

## 5.12 拥塞控制进阶例题

### 5.12.1 完整拥塞控制过程计算

> [!example] 综合例题
> 已知TCP连接的MSS = 1KB，初始cwnd = 1，ssthresh = 16。在传输过程中：
> - 第4个RTT结束时收到3个重复ACK
> - 第10个RTT结束时发生超时
> - 第15个RTT结束时又收到3个重复ACK
>
> 求各RTT的cwnd和ssthresh值。
>
> **解答**：
>
> | RTT | cwnd(KB) | ssthresh | 阶段 | 说明 |
> |-----|----------|----------|------|------|
> | 1 | 1 | 16 | 慢开始 | cwnd×2 |
> | 2 | 2 | 16 | 慢开始 | cwnd×2 |
> | 3 | 4 | 16 | 慢开始 | cwnd×2 |
> | 4 | — | — | — | **收到3个重复ACK**：ssthresh=4/2=2，cwnd=ssthresh=2（快恢复） |
> | 5 | 2 | 2 | 拥塞避免 | +1 |
> | 6 | 3 | 2 | 拥塞避免 | +1 |
> | 7 | 4 | 2 | 拥塞避免 | +1 |
> | 8 | 5 | 2 | 拥塞避免 | +1 |
> | 9 | 6 | 2 | 拥塞避免 | +1 |
> | 10 | — | — | — | **超时**：ssthresh=6/2=3，cwnd=1（慢开始） |
> | 11 | 1 | 3 | 慢开始 | cwnd×2 |
> | 12 | 2 | 3 | 慢开始 | cwnd×2 |
> | 13 | 3 | 3 | 慢开始→拥塞避免 | cwnd=ssthresh，切换 |
> | 14 | 4 | 3 | 拥塞避免 | +1 |
> | 15 | — | — | — | **收到3个重复ACK**：ssthresh=4/2=2，cwnd=2（快恢复） |
> | 16 | 2 | 2 | 拥塞避免 | +1 |

### 5.12.2 拥塞控制关键规则总结

> [!important] 拥塞控制核心规则
> | 事件 | ssthresh更新 | cwnd更新 | 进入阶段 |
> |------|-------------|----------|----------|
> | cwnd < ssthresh时正常增长 | 不变 | ×2（每RTT） | 慢开始 |
> | cwnd ≥ ssthresh时正常增长 | 不变 | +1（每RTT） | 拥塞避免 |
> | **超时** | cwnd/2 | **1** | 慢开始 |
> | **3个重复ACK** | cwnd/2 | **ssthresh** | 快恢复→拥塞避免 |
>
> 关键区别：
> - **超时** → cwnd归1，重新慢开始（认为网络严重拥塞）
> - **3个重复ACK** → cwnd减半，快恢复（认为网络轻度拥塞，部分报文仍能到达）

### 5.12.3 TCP版本对比

| TCP版本 | 拥塞控制策略 | 特点 |
|---------|-------------|------|
| **TCP Tahoe** | 慢开始 + 拥塞避免 + 快重传 | 超时和3个重复ACK都cwnd=1 |
| **TCP Reno** | Tahoe + 快恢复 | 3个重复ACK时cwnd=ssthresh（不归1） |
| **TCP NewReno** | Reno改进 | 对同一窗口内多个丢失更好处理 |
| **TCP Vegas** | 基于RTT延迟 | 通过RTT变化检测拥塞，而非丢包 |
| **TCP Cubic** | 三次函数增长 | 现代Linux默认，适合高带宽网络 |

> [!note] 408考试范围
> - 408考试中默认使用**TCP Reno**版本
> - 即超时→cwnd=1（慢开始），3个重复ACK→cwnd=ssthresh（快恢复）

> 3. TCP选项字段（MSS、窗口扩大、时间戳、SACK的作用与使用场景）
> 4. 三次握手与四次挥手的详细过程及状态转换
> 5. 为什么需要三次握手？为什么需要TIME-WAIT等待2MSL？
> 6. SYN泛洪攻击原理与SYN Cookie防御机制
> 7. TCP滑动窗口机制与流量控制计算
> 8. 零窗口探测与持续计时器（防止死锁）
> 9. TCP拥塞控制的四种算法（慢开始、拥塞避免、快重传、快恢复）
> 10. 拥塞窗口变化过程计算（超时 vs 3个重复ACK的处理差异）
> 11. TCP序号与确认号的计算（含SYN/FIN消耗序号）
> 12. 累积确认与SACK的原理及与GBN/SR的关系
> 13. RTO自适应计算与Karn算法
> 14. Nagle算法、延迟确认与糊涂窗口综合症
> 15. TCP半关闭的概念与应用场景
> 16. 复用与分用的概念（UDP按端口分用，TCP按四元组分用）
> 17. 常见端口号
> 18. UDP伪首部的作用与校验和计算

> [!note] 易错点
> - TCP序号是**字节编号**，不是报文段编号
> - 确认号表示**期望收到的下一个字节**的编号
> - SYN和FIN虽不携带数据，但各**消耗一个序号**
> - **第一次SYN没有ACK标志**（无东西可确认，ACK=0时确认号字段无意义）
> - **乱序段只暂存不交付**，ACK停在缺口处不动，收到缺口段后一口气跳进
> - 超时触发慢开始（cwnd=1），3个重复ACK触发快恢复（cwnd=ssthresh）
> - 流量控制是**端到端**的（rwnd由接收方通告），拥塞控制是**全局**的（cwnd由发送方调整）
> - 发送窗口 = min(rwnd, cwnd)，两者取较小值
> - UDP校验和计算时需要加12字节的**伪首部**（不实际传输）
> - MSS = MTU - IP首部(20) - TCP首部(20)，以太网典型MSS = 1460
> - Karn算法：重传报文段的RTT**不用于**更新RTT_S
> - 首部长度字段以**4字节**为单位，最小值5（20字节），最大值15（60字节）
> - Nagle算法与延迟确认同时使用会产生**额外延迟**
> - TCP分用依据**四元组**，UDP分用仅依据**目的端口**
> - 同时打开建立连接需要**9个报文段**，同时关闭双方都进入TIME-WAIT
> - 408考试默认使用**TCP Reno**版本（3个重复ACK不归1，而是cwnd=ssthresh）

> [!tip] 计算题速记公式
> - 发送窗口 = min(rwnd, cwnd)
> - MSS = MTU - 40
> - 慢开始：cwnd每RTT翻倍（cwnd×2）
> - 拥塞避免：cwnd每RTT加1（cwnd+1）
> - 超时：ssthresh = cwnd/2，cwnd = 1
> - 3个重复ACK：ssthresh = cwnd/2，cwnd = ssthresh
> - RTO = RTT_S + 4 × RTT_D
> - RTT_S = (1-α)×RTT_S + α×RTT_new（α=0.125）
> - RTT_D = (1-β)×RTT_D + β×|RTT_S - RTT_new|（β=0.25）

> [!important] 各层校验范围对比
> | 层次 | 校验内容 | 校验方式 |
> |------|----------|----------|
> | 数据链路层 | 帧的差错检测 | CRC循环冗余校验 |
> | 网络层（IP） | **仅首部** | 首部检验和（每跳重新计算） |
> | 传输层（UDP/TCP） | **首部+数据+伪首部** | 反码求和校验和 |
> | 应用层 | 视协议而定 | 各应用自定义 |
